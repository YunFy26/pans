# C++ 并发同步机制

并发程序允许多个执行单元在重叠的时间范围内推进任务。它能够提高处理器利用率、缩短独立任务的总体完成时间，但也会引入共享状态访问、执行顺序控制和线程生命周期管理等问题。同步机制的作用，是在多个线程之间建立必要的互斥关系与先后关系，使程序在所有符合语言规则的执行次序下都保持正确。

本文以 C++ 标准库为主，系统说明互斥量、自旋、条件变量、信号量、闩锁、屏障、原子操作和异步结果传递，并讨论死锁、活锁、ABA、伪共享等问题。除专门说明外，示例以 C++20 为标准。
- `std::mutex`、`std::future` 和基本原子类型从 C++11 开始提供
- `std::shared_timed_mutex` 从 C++14 开始提供 
- `std::shared_mutex` 与 `std::scoped_lock` 从 C++17 开始提供
- 信号量、闩锁、屏障、`std::atomic_ref` 及原子等待通知从 C++20 开始提供
- POSIX 自旋锁不属于 C++ 标准库，其可用性取决于操作系统和线程库。

同步机制首先服务于正确性。只有在数据竞争等问题已经得到控制后，吞吐量、延迟与资源消耗方面的优化才具有实际意义。

## 1. 并发与同步基础

### 1.1 并发、并行与异步

并发描述多个任务在同一时间区间内交替或重叠推进。即使处理器只有一个核心，操作系统也可以通过时间片调度形成并发。并行描述多个任务在同一时刻分别由不同处理器核心执行。

异步描述发起操作后，调用者不必在原地等待操作完成。异步操作可以由另一个线程执行，也可以由操作系统事件机制、设备或运行时系统推进。异步不必然意味着并行，例如延迟执行的 `std::async` 任务可能直到调用 `get()` 时才在当前线程执行。

三者关注的角度不同：并发关注任务推进方式，并行关注同一时刻的实际执行，异步关注操作发起与结果取得之间是否解耦。一个程序可以采用异步接口但只在单线程上执行，也可以采用多个同步线程在多核处理器上并行执行。

### 1.2 线程与共享状态

线程拥有独立的调用栈、寄存器状态和执行位置。同一进程中的线程通常共享代码段、全局对象、静态对象和动态分配的内存。共享使线程间通信较为简单，但某个线程的写入可能影响其他线程。

最容易管理的并发结构是尽量减少可变共享状态。例如，可以采用不可变对象、值传递、线程局部存储和所有权转移。确实需要共享修改时，再使用互斥量、原子操作或消息传递维护明确的不变量。

### 1.3 数据竞争

按照 C++ 内存模型，如果两个可能并发发生的求值访问同一个内存位置，其中至少一个访问会修改该位置，两个访问都不是适当的原子操作，并且二者之间没有建立规定的先行发生关系，就会产生数据竞争。数据竞争会导致未定义行为。

在多线程模式下，下面的计数器存在数据竞争：

```cpp
int counter = 0;

void increment()
{
    ++counter;
}
```

`++counter` 通常包含读取、加一和写回。多个线程的步骤可能交错并造成更新丢失。

消除数据竞争的常用方法包括：
- 使用同一互斥量保护所有相关访问；
- 将对象改为适当的原子类型；
- 让共享对象在发布后保持只读；
- 重新设计所有权，使同一时刻只有一个线程能够修改对象。

### 1.4 竞态条件

竞态条件是更广义的逻辑概念，表示程序结果依赖于并发事件的相对先后次序，并且某些次序会产生错误。数据竞争由 C++ 内存模型严格定义，而竞态条件可能发生在完全没有数据竞争的程序中。

例如，下面的两个操作都可以在互斥量保护下分别保持线程安全，但先检查再执行仍可能形成竞态条件：

```cpp
if (!queue.empty()) {
    auto value = queue.pop();
}

// 初始队列：[A]
// 线程 1                    线程 2
// empty() == false
//                           empty() == false
//                           pop() 取走 A
// pop() 发现队列为空
```

如果 `empty()` 和 `pop()` 各自在内部独立加锁，另一个线程仍可能在两次调用之间取走最后一个元素。解决方法不是为单个成员函数增加更多锁，而是提供把检查与取出合并为一次原子业务操作的接口，例如 `try_pop()`。
```cpp
std::optional<T> try_pop()
{
    std::lock_guard<std::mutex> lock(mutex_);

    if (queue_.empty()) {
        return std::nullopt;
    }

    T value = std::move(queue_.front());
    queue_.pop();
    return value;
}
```
因此，没有数据竞争并不等于并发逻辑正确。审查并发程序还需要检查状态转换、复合不变量和跨函数操作是否保持原子业务语义。

### 1.5 临界区

临界区是访问共享状态并要求互斥执行的代码区域。进入临界区前取得锁，离开时释放锁，可以防止其他线程同时修改受保护状态。

```cpp
#include <mutex>

std::mutex counter_mutex;
int counter = 0;

void increment()
{
    std::lock_guard<std::mutex> lock(counter_mutex);
    // 这里临界区只有 ++counter;
    ++counter;
}
```

临界区的边界应覆盖完整不变量。例如，账户转账需要同时验证余额并修改两个账户，只保护其中一次赋值并不能维护资金总额不变。另一方面，临界区也不宜无必要地包含文件 I/O、网络等待、长时间计算或未知回调，因为这些操作会延长其他线程的等待时间，并增加死锁风险。

### 1.6 互斥与同步

互斥保证受保护操作不会在同一时间交错执行。同步的含义更广，还包括执行顺序、等待条件、阶段汇合和内存可见性。

对某个互斥量的解锁与另一个线程随后成功取得同一互斥量之间会建立同步关系。取得锁的线程不仅获得进入临界区的资格，也能够观察到前一个持锁线程在解锁前完成的相关写入。条件变量、信号量和具有适当内存顺序的原子操作也可以建立同步关系。

互斥量适合保护由多个字段构成的不变量；原子操作适合独立标志、计数和经过严格设计的状态机；条件变量适合等待由共享状态描述的条件；阶段同步设施适合线程汇合。机制应当按照状态结构选择，而不是只按照单次操作的表面开销选择。

### 1.7 原子性、可见性与有序性

原子性表示某个操作从其他线程的观察角度不可分割。对 `std::atomic<int>` 的一次 `fetch_add` 是原子读改写操作，不会与同一原子对象上的其他原子修改相互撕裂。

可见性表示一个线程完成的写入能够被另一个线程观察到。普通对象的跨线程可见性需要通过互斥量或具有相应内存顺序的原子操作建立。处理器缓存最终可能传播数据，并不能替代 C++ 语言层面的同步关系。

有序性表示求值之间受到编译器、处理器和语言内存模型所规定的顺序约束。编译器和处理器可以在不改变单线程可观察行为的前提下重排操作。release 与 acquire 配对可以限制相关操作跨越同步边界，从而发布普通数据。

这三个性质不能相互替代。`memory_order_relaxed` 原子操作保证该原子对象上的操作不可分割，并参与该对象的修改顺序，但通常不负责发布其他普通对象。互斥量则同时提供排他访问和明确的同步边界。

### 1.8 阻塞等待与忙等待

阻塞等待表示暂时无法继续的线程由运行库或操作系统挂起(不占用CPU)，等待条件满足后再进入可运行状态。它能够节省处理器时间，但睡眠、唤醒和上下文切换会产生开销。

忙等待表示线程反复检查条件。自旋锁和简单的原子轮询属于忙等待。等待非常短且处理器核心充足时，自旋代价要比调度开销更小；等待变长、竞争升高或线程数量超过硬件执行资源时，自旋会消耗大量 CPU，并可能妨碍持锁线程获得执行机会。

实际实现经常采用混合策略：先自旋少量次数，仍未成功时进入阻塞等待。

## 2. 基于互斥量的同步

### 2.1 独占互斥量

`std::mutex` 是 C++11 提供的基本独占互斥量。同一时刻至多有一个线程持有某个互斥量。它提供 `lock()`、`try_lock()` 和 `unlock()`：`lock()` 等待直到取得所有权；`try_lock()` 只进行一次非阻塞尝试并返回结果；`unlock()` 释放当前线程拥有的互斥量。

直接管理加锁与解锁容易在异常和提前返回路径上遗漏释放，因此一般应由 RAII 锁管理器完成：

```cpp
#include <cstddef>
#include <mutex>
#include <vector>

class SafeVector {
public:
    void push(int value)
    {
        std::lock_guard<std::mutex> lock(mutex_);
        values_.push_back(value);
    }

    std::size_t size() const
    {
        std::lock_guard<std::mutex> lock(mutex_);
        return values_.size();
    }

private:
    mutable std::mutex mutex_;
    std::vector<int> values_;
};
```

互斥量与被保护数据应具有容易识别的关联。常见做法是把互斥量和数据封装在同一类中，并避免返回指向内部可变对象的引用或指针，否则调用者可能在锁已经释放后访问共享数据。

`std::mutex` 适合一般共享对象、复合不变量和临界区长度不可忽略的场景。它不可复制，不提供递归加锁语义，也不保证特定的公平调度顺序。对未持有的互斥量调用 `unlock()`，或者让拥有互斥量的线程在未释放时终止，都会违反接口前置条件。

### 2.2 定时互斥量

`std::timed_mutex` 在普通互斥量基础上增加限时尝试。`try_lock_for(duration)` 最多等待一个相对时长，`try_lock_until(time_point)` 最多等待到某个绝对时间点。两者在成功时返回 `true`，超时或尝试失败时返回 `false`。

```cpp
#include <chrono>
#include <mutex>

std::timed_mutex resource_mutex;

bool update_with_timeout()
{
    using namespace std::chrono_literals;

    std::unique_lock<std::timed_mutex> lock(
        resource_mutex,
        50ms
    );
    if (!lock.owns_lock()) {
        return false;
    }

    return true;
}
```

限时等待适合需要取消、降级或故障恢复的场景。超时不应只被理解为性能异常，它还可能表示系统负载过高、锁竞争、持锁线程阻塞或潜在死锁。程序需要明确超时后的状态：可以返回错误、记录诊断信息、采用只读缓存结果，或者在更高层重新尝试。

相对时长通常由稳定时钟实现更合适，绝对截止时间则应注意所用时钟是否可能发生调整。标准允许定时等待受到调度延迟影响，因此实际返回时间可能晚于请求的截止时间。

### 2.3 递归互斥量

`std::recursive_mutex` 允许同一线程重复取得同一把锁。内部会维护递归层数，每次成功加锁增加计数，每次解锁减少计数，只有计数降为零时其他线程才可能取得锁。`std::recursive_timed_mutex` 进一步提供限时尝试。

递归互斥量可用于无法立即重构的递归调用关系，例如一个已持锁的成员函数调用另一个也按照公共接口规则加锁的成员函数。然而，它会掩盖锁所有权和调用层次，使临界区扩大，也容易造成加锁与解锁次数不匹配。

优先的设计通常是把接口分为加锁入口和要求调用者已经持锁的内部实现：

```cpp
#include <mutex>

class Counter {
public:
    void add(int amount)
    {
        std::lock_guard<std::mutex> lock(mutex_);
        add_unlocked(amount);
    }

    void add_twice(int amount)
    {
        std::lock_guard<std::mutex> lock(mutex_);
        add_unlocked(amount);
        add_unlocked(amount);
    }

private:
    void add_unlocked(int amount)
    {
        value_ += amount;
    }

    std::mutex mutex_;
    int value_ = 0;
};
```

这种结构明确了只有公共入口负责加锁，内部函数依赖既定锁前置条件。只有在递归所有权确实是领域模型的一部分，或重构成本暂时不可接受时，才应考虑递归互斥量。

### 2.4 共享互斥量

`std::shared_mutex` 支持共享模式与独占模式。多个读取者可以同时取得共享所有权，写入者需要取得独占所有权，并排斥全部读取者和其他写入者。C++14 的 `std::shared_timed_mutex` 还支持共享与独占模式下的限时尝试。

```cpp
#include <mutex>
#include <shared_mutex>
#include <string>
#include <unordered_map>
#include <utility>

class Dictionary {
public:
    std::string find(const std::string& key) const
    {
        std::shared_lock<std::shared_mutex> lock(mutex_);
        const auto it = data_.find(key);
        return it == data_.end() ? std::string{} : it->second;
    }

    void insert_or_assign(std::string key, std::string value)
    {
        std::unique_lock<std::shared_mutex> lock(mutex_);
        data_.insert_or_assign(std::move(key), std::move(value));
    }

private:
    mutable std::shared_mutex mutex_;
    std::unordered_map<std::string, std::string> data_;
};
```

共享锁只有在读取比例高、读临界区具有一定工作量，并且并发读取确实能够重叠时才可能带来收益。对于极短读取，复杂的共享状态管理可能比普通互斥量开销更大。如果写入频繁，共享互斥量也可能退化为频繁的全局排他。

C++ 标准没有为所有共享互斥量规定统一的读写公平策略。具体实现可能偏向读取者、偏向写入者或采用阶段性策略，因此持续读取可能延迟写入，持续写入也可能影响读取延迟。对公平性有硬性要求时，应查阅目标实现并进行压力测试，必要时在更高层设计排队或配额机制。

标准共享互斥量不提供可移植的原地升级操作。先持有共享锁再直接请求独占锁可能发生自我死锁。通常需要释放共享锁后重新取得独占锁，并在独占锁下重新检查条件。

### 2.5 多互斥量管理

当一个操作同时维护多个资源的不变量时，可能需要同时取得多把互斥量。例如账户转账需要同时锁定转出账户与转入账户。若不同线程采用相反的加锁顺序，就可能形成死锁。

`std::lock` 能够使用避免死锁的算法取得多把锁，但调用者仍需用 `std::adopt_lock` 把已取得的锁交给 RAII 对象管理。C++17 的 `std::scoped_lock` 直接组合了这两个步骤：

```cpp
#include <mutex>
#include <stdexcept>

struct Account {
    std::mutex mutex;
    long long balance = 0;
};

void transfer(Account& from, Account& to, long long amount)
{
    if (&from == &to) {
        return;
    }
    if (amount < 0) {
        throw std::invalid_argument("amount must be non-negative");
    }

    std::scoped_lock lock(from.mutex, to.mutex);
    if (from.balance < amount) {
        throw std::runtime_error("insufficient balance");
    }

    from.balance -= amount;
    to.balance += amount;
}
```

`std::try_lock` 依次尝试多把锁，全部成功时返回 `-1`；失败时返回未能取得的锁在参数序列中的索引，并释放本次调用此前已经取得的锁。它适合调用者需要非阻塞尝试并自行决定失败处理的场景。

固定的全局加锁顺序也是重要方法。例如为资源分配稳定编号，并始终先锁编号较小者。该规则必须覆盖整个程序，局部一致但跨模块不一致仍可能形成环路。能够一次性取得全部锁时，优先使用 `std::scoped_lock` 表达意图。

### 2.6 RAII 锁管理工具

RAII 将锁的所有权绑定到对象生命周期。锁管理器构造时取得或接管锁，析构时释放锁，使异常、提前返回和多分支控制流都能保持资源释放规则。

`std::lock_guard` 体积小、语义固定，适合在整个作用域内始终持锁。`std::unique_lock` 支持延迟加锁、尝试加锁、限时加锁、提前解锁、重新加锁和所有权转移，也是 `std::condition_variable` 等待所需的锁类型。`std::shared_lock` 以 RAII 方式管理共享所有权。`std::scoped_lock` 适合同时管理一把或多把互斥量。

标准标签用于选择构造方式：

- `std::defer_lock`：构造管理器但暂不加锁，之后可以调用 `lock()`，或交给 `std::lock` 同时取得多把锁。
- `std::try_to_lock`：构造时只尝试一次，随后用 `owns_lock()` 检查结果。
- `std::adopt_lock`：接管调用者已经拥有的锁。若调用者实际没有持锁，行为不符合前置条件。

下面的代码使用 `defer_lock` 和 `std::lock` 管理两个资源：

```cpp
#include <mutex>
#include <utility>

void swap_values(int& left, std::mutex& left_mutex,
                 int& right, std::mutex& right_mutex)
{
    if (&left == &right) {
        return;
    }

    std::unique_lock<std::mutex> left_lock(
        left_mutex,
        std::defer_lock
    );
    std::unique_lock<std::mutex> right_lock(
        right_mutex,
        std::defer_lock
    );
    std::lock(left_lock, right_lock);
    std::swap(left, right);
}
```

自定义锁只要提供相应接口，也能与标准管理器配合。基本 `Lockable` 形式需要 `lock()` 和 `unlock()`；支持尝试加锁时还需 `try_lock()`；支持定时操作时还需相应的 `try_lock_for()` 和 `try_lock_until()`。接口的异常保证和所有权规则必须与标准锁要求一致。

## 3. 自旋与混合等待机制

### 3.1 自旋锁

自旋锁在锁被占用时持续尝试，而不是立即阻塞当前线程。它通过忙等待换取避免睡眠和唤醒的机会，只适用于预期等待时间非常短的场景。

`std::atomic_flag` 是实现简单自旋锁的常用基础。加锁使用原子测试并置位，解锁清除标志。成功加锁应具有 acquire 语义，解锁应具有 release 语义，以保证临界区内普通读写不会跨越锁边界：

```cpp
#include <atomic>

class SpinLock {
public:
    SpinLock() noexcept = default;

    SpinLock(const SpinLock&) = delete;
    SpinLock& operator=(const SpinLock&) = delete;

    void lock() noexcept
    {
        while (flag_.test_and_set(std::memory_order_acquire)) {
            while (flag_.test(std::memory_order_relaxed)) {
                cpu_relax();
            }
        }
    }

    bool try_lock() noexcept
    {
        return !flag_.test_and_set(std::memory_order_acquire);
    }

    void unlock() noexcept
    {
        flag_.clear(std::memory_order_release);
    }

private:
    static void cpu_relax() noexcept
    {
#if defined(__x86_64__) || defined(__i386__)
        __builtin_ia32_pause();
#elif defined(__aarch64__) || defined(__arm__)
        __asm__ __volatile__("yield");
#endif
    }

    std::atomic_flag flag_ = ATOMIC_FLAG_INIT;
};
```

外层 `test_and_set` 负责竞争锁，内层只读 `test` 降低多个等待者持续写同一缓存行造成的一致性流量。`atomic_flag::test` 从 C++20 开始提供。该类具有 `lock`、`try_lock` 和 `unlock`，因而可以交给 `std::lock_guard<SpinLock>` 或 `std::scoped_lock` 管理。

自旋锁的正确实现不只涉及原子标志。还需要考虑处理器提示、退避、公平性、抢占、异常边界和目标平台。普通应用代码通常应先使用标准互斥量，只有性能分析确认锁睡眠或唤醒成本构成瓶颈时，才应引入自定义自旋锁。

### 3.2 自旋优化

紧密轮询会占用执行单元，并持续产生缓存一致性流量。x86 的 `PAUSE`、ARM 的 `YIELD` 等处理器提示可以改善自旋循环对流水线和同步多线程资源的影响，但它们不提供内存同步，也不保证线程进入睡眠。

退避策略在连续失败后减少尝试频率。固定退避每次等待相同数量的处理器周期，结构简单，但无法适应竞争变化。指数退避从较短延迟开始，在连续失败后逐步扩大等待窗口，并设置上限，能够降低大量线程同时争抢同一缓存行造成的冲突。

达到退避上限后，可以调用 `std::this_thread::yield()` 让出当前时间片的剩余执行机会。`yield()` 只是向调度器提供提示，不保证另一个特定线程立即运行，也可能很快返回。对于可能持续较长的等待，更合理的做法是转入阻塞机制，而不是无限次让出后继续轮询。

退避参数与处理器、线程数量、临界区长度和调度策略有关，不存在适合所有平台的固定值。参数必须在目标负载上测量，并同时观察吞吐量、尾延迟和 CPU 使用率。

### 3.3 POSIX 自旋锁

POSIX 提供 `pthread_spinlock_t` 及以下操作：`pthread_spin_init` 初始化，`pthread_spin_destroy` 销毁，`pthread_spin_lock` 阻塞式自旋取得锁，`pthread_spin_trylock` 进行非阻塞尝试，`pthread_spin_unlock` 释放锁。

```cpp
#include <cerrno>
#include <exception>
#include <pthread.h>
#include <system_error>

class PosixSpinLock {
public:
    PosixSpinLock()
    {
        const int result = pthread_spin_init(
            &lock_,
            PTHREAD_PROCESS_PRIVATE
        );
        if (result != 0) {
            throw std::system_error(result, std::generic_category());
        }
    }

    ~PosixSpinLock()
    {
        if (pthread_spin_destroy(&lock_) != 0) {
            std::terminate();
        }
    }

    PosixSpinLock(const PosixSpinLock&) = delete;
    PosixSpinLock& operator=(const PosixSpinLock&) = delete;

    void lock()
    {
        const int result = pthread_spin_lock(&lock_);
        if (result != 0) {
            throw std::system_error(result, std::generic_category());
        }
    }

    bool try_lock()
    {
        const int result = pthread_spin_trylock(&lock_);
        if (result == 0) {
            return true;
        }
        if (result == EBUSY) {
            return false;
        }
        throw std::system_error(result, std::generic_category());
    }

    void unlock() noexcept
    {
        const int result = pthread_spin_unlock(&lock_);
        if (result != 0) {
            std::terminate();
        }
    }

private:
    pthread_spinlock_t lock_{};
};
```

`PTHREAD_PROCESS_PRIVATE` 表示锁只供当前进程内线程使用。`PTHREAD_PROCESS_SHARED` 用于进程间共享，但锁对象必须位于共享内存中，而且目标实现必须支持该模式。

POSIX 自旋锁不是 C++ 标准设施，可移植性有限。Linux 上通常可用，常见 macOS 开发环境不提供 `pthread_spinlock_t`。错误码、销毁前置条件和进程共享支持也应按照目标系统文档确认。若项目需要跨平台，通常应封装平台差异或使用标准互斥量。

### 3.4 自适应锁

自适应锁先进行有限自旋，若锁在短时间内释放即可避免阻塞；自旋失败后再进入内核或运行库等待。该策略适合锁保持时间通常很短、但偶尔也会出现长等待的负载。

自旋次数可以采用固定阈值，也可以根据历史持锁时间、当前处理器数量、持锁线程是否正在运行和近期竞争强度动态调整。阈值过低会频繁进入阻塞路径，阈值过高会浪费处理器资源。

许多操作系统和线程运行库已经在普通互斥量内部采用适应性策略。应用层通常无法也不需要依赖具体实现细节。自行在标准互斥量外再增加长时间自旋，可能与底层策略重复，并降低可维护性。

### 3.5 自旋锁的适用条件

判断是否采用自旋锁，需要同时评估以下因素：

- 临界区长度：临界区必须很短且执行时间可预测，不应包含阻塞操作。
- 竞争程度：无竞争时自旋锁路径较短，高竞争时大量线程会消耗 CPU 并争用缓存行。
- CPU 核心数量：需要有足够核心让持锁线程继续运行；单核或严重过度订阅时自旋通常不利。
- 抢占与调度：持锁线程被抢占后，其他线程只能持续等待。实时优先级差异还可能放大问题。
- 公平性：简单测试并置位锁通常没有排队公平性，某些线程可能长期失败。
- 可移植性：处理器提示、缓存拓扑和平台线程接口存在差异。

自旋锁不应仅凭一次微基准结果投入生产。需要在真实核心数量、线程亲和性和负载分布下验证，并关注尾延迟、处理器占用、热功耗和持锁线程被抢占时的退化行为。

## 4. 条件等待与通知

### 4.1 条件变量原理

条件变量用于等待由共享状态描述的条件。它本身不保存业务条件，真正的条件必须由受互斥量保护的谓词表示。例如，队列非空、系统正在停止或可用容量大于零都可以作为谓词。

等待操作需要把解锁与进入等待状态作为一个协调过程完成，否则会出现以下时间窗口：等待线程先发现条件不成立，通知线程随后修改状态并发出通知，等待线程最后才进入睡眠。此时通知已经发生，等待线程可能永久等待。条件变量的 `wait` 通过与互斥量配合关闭这一窗口。

等待过程可以概括为：调用者持有锁并检查谓词；条件不满足时，`wait` 原子地释放锁并加入等待；线程被唤醒后重新取得锁；再次检查谓词。等待队列由条件变量实现管理，但业务状态仍由程序自己的对象保存。

通知不具有可累积的事件计数。如果通知发生时没有满足条件的等待者，后续等待不能仅依靠这次通知继续。因此，先修改受保护状态，再以循环或带谓词重载等待，是正确模式的核心。

条件变量允许虚假唤醒，即线程可能在没有对应通知、或者条件仍不满足时返回等待调用。即使不存在虚假唤醒，多个等待者竞争同一资源时，某个线程取得锁前条件也可能再次变化。因此每次唤醒后都必须重新检查谓词。

### 4.2 `std::condition_variable`

`std::condition_variable` 与 `std::unique_lock<std::mutex>` 配合。之所以不能只使用 `std::lock_guard`，是因为等待期间需要显式释放互斥量，并在返回前重新取得所有权。

`wait(lock)` 执行无期限等待；`wait(lock, predicate)` 在内部反复检查谓词。`wait_for` 接受相对时长，`wait_until` 接受绝对时间点。定时等待也应使用带谓词形式或在循环中计算统一截止时间，避免虚假唤醒使多次相对等待不断延长总时限。

`notify_one()` 唤醒一个等待者，适合一次状态变化只允许一个线程继续的场景。`notify_all()` 唤醒全部等待者，适合全局状态切换、关闭或多个等待者可能满足不同条件的场景。通知不保证等待者立刻运行，也不规定确定的选择顺序。

下面是一个支持关闭的有界阻塞队列：

```cpp
#include <condition_variable>
#include <cstddef>
#include <deque>
#include <mutex>
#include <optional>
#include <stdexcept>
#include <utility>

template <class T>
class BoundedQueue {
public:
    explicit BoundedQueue(std::size_t capacity)
        : capacity_(capacity)
    {
        if (capacity_ == 0) {
            throw std::invalid_argument("capacity must be positive");
        }
    }

    bool push(T value)
    {
        std::unique_lock<std::mutex> lock(mutex_);
        not_full_.wait(lock, [this] {
            return closed_ || queue_.size() < capacity_;
        });

        if (closed_) {
            return false;
        }

        queue_.push_back(std::move(value));
        lock.unlock();
        not_empty_.notify_one();
        return true;
    }

    std::optional<T> pop()
    {
        std::unique_lock<std::mutex> lock(mutex_);
        not_empty_.wait(lock, [this] {
            return closed_ || !queue_.empty();
        });

        if (queue_.empty()) {
            return std::nullopt;
        }

        T value = std::move(queue_.front());
        queue_.pop_front();
        lock.unlock();
        not_full_.notify_one();
        return value;
    }

    void close()
    {
        {
            std::lock_guard<std::mutex> lock(mutex_);
            closed_ = true;
        }
        not_empty_.notify_all();
        not_full_.notify_all();
    }

private:
    const std::size_t capacity_;
    std::mutex mutex_;
    std::condition_variable not_empty_;
    std::condition_variable not_full_;
    std::deque<T> queue_;
    bool closed_ = false;
};
```

状态修改必须在锁内完成。通知可以在解锁前或解锁后调用，两种方式都能正确同步；在这个示例中先解锁再通知，可以减少被唤醒线程随即阻塞在同一互斥量上的机会。该选择不应破坏状态与谓词的保护规则。

### 4.3 `std::condition_variable_any`

`std::condition_variable_any` 是更通用的条件变量，可以配合满足基本锁要求的类型，而不限于 `std::unique_lock<std::mutex>`。它可用于自定义锁、`std::unique_lock<SpinLock>`，也可以在设计合理时配合 `std::shared_lock<std::shared_mutex>`。

通用性通常需要额外的类型擦除或间接调用，因此 `std::condition_variable` 在只需要普通互斥量时往往具有更直接的实现。选择两者的依据应是锁类型需求，而不是把 `condition_variable_any` 视为功能更强的默认替代。

使用共享锁等待时要特别谨慎。等待会释放并重新取得共享所有权，修改谓词的线程仍应在独占锁下更新状态。若多个读取者等待的条件本身需要写操作才能推进，就要确认通知路径不会被共享锁持有方式阻塞。

### 4.4 典型使用模式

生产者与消费者模式由生产者写入任务、消费者取出任务。无界队列通常只需要非空条件；有界队列还需要非满条件，以施加背压并限制内存增长。

状态变化通知适合等待复杂谓词。例如线程可以等待 `stopped || generation != observed_generation`，从而同时响应关闭和版本变化。谓词应只读取由同一把锁保护的状态，并保持执行快速，不应在谓词中进行阻塞操作。

线程安全任务队列还需要明确生命周期语义：关闭后是否允许继续提交；队列中剩余任务是否处理完；等待线程如何退出；任务异常由何处接收。单纯的 `notify_all()` 不能替代关闭标志，否则没有任务的消费者在唤醒后仍会重新进入等待。

正确模式可以归纳为四个步骤：在互斥量保护下读取或修改状态；使用谓词循环等待；状态改变后进行适当通知；在关闭与异常路径上唤醒所有可能永久等待的线程。

## 5. 计数与阶段同步

### 5.1 信号量

信号量维护一个非负许可计数。`acquire()` 等待并消耗一个许可，`try_acquire()` 进行非阻塞尝试，`release(n)` 增加许可并使相应等待者有机会继续。C++20 的 `std::counting_semaphore<LeastMaxValue>` 表示计数信号量，`std::binary_semaphore` 是最大计数至少为 1 的常用二值形式。

下面的信号量把并发访问外部服务的操作限制为最多四个：

```cpp
#include <semaphore>
#include <utility>

void perform_request();

class Permit {
public:
    explicit Permit(std::counting_semaphore<>& semaphore)
        : semaphore_(semaphore)
    {
        semaphore_.acquire();
    }

    ~Permit()
    {
        semaphore_.release();
    }

    Permit(const Permit&) = delete;
    Permit& operator=(const Permit&) = delete;

private:
    std::counting_semaphore<>& semaphore_;
};

std::counting_semaphore<> service_slots(4);

void call_service()
{
    Permit permit(service_slots);
    perform_request();
}
```

其中 `perform_request()` 代表程序中已有的实际请求函数，`Permit` 保证作用域退出时归还许可。实际工程中还应为请求设置超时和取消策略。

信号量适合限制并发数量、表示资源池中的可用项或在线程间传递许可。互斥量表示所有权，同一线程取得后通常应由该线程释放；信号量表示计数，许可可以由一个线程释放并由另一个线程取得。二值信号量虽然计数范围类似互斥量，但不自动形成受保护临界区的所有权纪律。

### 5.2 闩锁

`std::latch` 是一次性递减计数器。构造时给定参与计数，线程调用 `count_down()` 表示完成一个单位，调用 `wait()` 等待计数归零，`arrive_and_wait()` 则先递减再等待。

```cpp
#include <latch>
#include <thread>
#include <vector>

void initialize_all(std::vector<int>& values)
{
    std::latch ready(values.size());
    std::vector<std::thread> threads;
    threads.reserve(values.size());

    for (std::size_t i = 0; i < values.size(); ++i) {
        threads.emplace_back([&, i] {
            values[i] = static_cast<int>(i * i);
            ready.count_down();
        });
    }

    ready.wait();

    for (auto& thread : threads) {
        thread.join();
    }
}
```

闩锁适合一次性线程汇合，例如等待全部服务完成初始化、等待一批独立任务结束或构造基准测试的起跑门。计数到零后不能重置，也不能进入下一轮。调用 `count_down` 的总递减量不能超过当前计数。

### 5.3 屏障

`std::barrier` 用于可重复的阶段同步。参与者到达当前阶段后等待，最后一个参与者到达时触发阶段完成步骤，随后全部参与者进入下一阶段。

`arrive()` 记录到达并返回一个到达令牌；`wait(token)` 使用令牌等待阶段推进；`arrive_and_wait()` 合并二者；`arrive_and_drop()` 表示当前阶段到达后永久退出后续阶段，并减少以后阶段的预期参与者数量。

```cpp
#include <barrier>
#include <cstddef>
#include <thread>
#include <vector>

void run_phases(std::vector<int>& values, std::size_t rounds)
{
    std::barrier<> phase_end(
        static_cast<std::ptrdiff_t>(values.size())
    );
    std::vector<std::thread> workers;
    workers.reserve(values.size());

    for (std::size_t i = 0; i < values.size(); ++i) {
        workers.emplace_back([&, i] {
            for (std::size_t round = 0; round < rounds; ++round) {
                values[i] += static_cast<int>(round + 1);
                phase_end.arrive_and_wait();
            }
        });
    }

    for (auto& worker : workers) {
        worker.join();
    }
}
```

完成阶段函数在阶段切换期间运行，适合汇总上一阶段结果、交换缓冲区或更新阶段编号。它必须快速、无异常，并避免等待同一屏障，否则会阻止所有参与者推进。屏障的内存同步保证使完成步骤及阶段前操作可以按照标准规定对下一阶段参与者可见。

### 5.4 机制比较

信号量与互斥量都能限制进入，但语义不同。互斥量保护临界区并跟踪所有权；信号量管理许可数量，可以允许多个线程同时进入。需要维护复合不变量时通常使用互斥量，需要限制资源并发度时通常使用计数信号量。

闩锁与屏障都能等待多个参与者。闩锁只能从初始计数下降到零一次，适合一次性完成事件；屏障在每一阶段自动建立下一轮，适合迭代算法和多阶段流水线。

条件变量与信号量都能唤醒等待者。条件变量不保存通知次数，必须与受锁保护的谓词配合；信号量保存许可计数，先发生的 `release` 可以供后续 `acquire` 使用。复杂状态条件适合条件变量，独立资源许可和事件计数适合信号量。

## 6. 原子操作与无锁同步

### 6.1 `std::atomic<T>`

`std::atomic<T>` 为特定对象提供原子访问。`load` 读取，`store` 写入，`exchange` 原子替换并返回旧值。整数原子类型还支持算术与位读改写操作，指针原子类型支持按元素进行的加减。所有针对同一原子对象的修改都处于一个一致的修改顺序中。

```cpp
#include <atomic>

std::atomic<unsigned long long> completed{0};
std::atomic<unsigned> flags{0};

void record_completion(unsigned flag)
{
    completed.fetch_add(1, std::memory_order_relaxed);
    flags.fetch_or(flag, std::memory_order_relaxed);
}
```

`fetch_add` 和 `fetch_sub` 原子增减并返回修改前的值；`fetch_and`、`fetch_or` 与 `fetch_xor` 进行位运算。相应运算符形式更简洁，但显式成员函数能够指定内存顺序，并明确返回旧值的语义。`++atomic_value` 等复合运算是原子的，而把原子对象先读取到普通变量再写回并不是一次原子读改写事务。

`volatile` 与 `atomic` 用途不同。`volatile` 主要用于实现相关的特殊内存访问，例如部分内存映射设备接口；它不为线程间访问提供原子性、互斥性或同步顺序。线程通信应使用原子类型或其他同步设施。

并非所有可平凡复制类型的原子实例都一定由硬件无锁实现。即使底层使用内部锁，只要符合标准接口，其操作仍具有规定的原子语义。

### 6.2 原子类型与辅助工具

`std::atomic_flag` 是最小的原子标志类型，支持测试并置位、清除以及 C++20 的读取和等待通知。它适合一次性状态、简单自旋锁和低层同步构件。

`std::atomic_ref<T>` 为已经存在的对象提供原子访问视图。只要某个 `atomic_ref` 仍与对象关联，同一对象的并发访问必须通过兼容的原子引用完成，不能同时进行冲突的普通访问。对象还必须满足对齐与类型要求，因此它适合无法把数据成员直接声明为原子类型、但生命周期和对齐能够严格控制的场景。

`std::atomic<T*>` 支持指针装载、存储、交换、比较交换和按元素大小进行的指针算术。指针值的原子更新不自动保护所指对象的生命周期，也不保证所指对象的内容可以无同步修改。无锁链表尤其需要安全内存回收方案。

成员函数 `is_lock_free()` 查询某个原子对象在当前执行中的实现属性，静态成员 `is_always_lock_free` 表示该类型在当前实现的所有对象是否始终无锁。结果依赖类型、对齐、ABI、处理器和标准库。无锁只表示系统整体能够继续推进的某类实现属性，不等于等待自由，也不等于更高性能。

### 6.3 比较并交换

比较并交换通常简称 CAS。它比较原子对象的当前值与 `expected`；相等时写入 `desired` 并返回 `true`，不相等时把当前值写回 `expected` 并返回 `false`。因此，失败后的 `expected` 不是原始期望值，而是下一轮重试可使用的最新观察值。

```cpp
#include <atomic>

void update_max(std::atomic<int>& maximum, int candidate)
{
    int observed = maximum.load(std::memory_order_relaxed);
    while (observed < candidate &&
           !maximum.compare_exchange_weak(
               observed,
               candidate,
               std::memory_order_relaxed,
               std::memory_order_relaxed)) {
    }
}
```

`compare_exchange_weak` 允许在值相等时仍出现伪失败，适合已经处于重试循环的场景，并可能在某些架构上生成更直接的指令。`compare_exchange_strong` 不允许这种伪失败，适合一次失败就具有业务含义、或者重试成本较高的场景。

比较交换可以分别指定成功与失败内存顺序。成功路径是读改写操作，可以使用 release、acquire 或 acq_rel；失败路径只进行读取，不能使用 `memory_order_release` 或 `memory_order_acq_rel`，并且不能提供强于成功路径所允许的同步保证。无法确认时应先采用默认的顺序一致语义，再通过证明和测量进行放宽。

CAS 循环的循环体必须容忍重复执行和 `expected` 更新。复杂状态需要尽可能编码到一次 CAS 的值中，否则多个独立原子对象之间仍可能破坏复合不变量。

### 6.4 原子等待与通知

C++20 为原子对象增加 `wait(old)`、`notify_one()` 和 `notify_all()`。`wait` 在原子值仍等于给定旧值时等待，并在返回前再次检查值。实现可以先短暂自旋，再使用操作系统等待原语，从而避免应用层无限忙等待。

```cpp
#include <atomic>

std::atomic<bool> ready{false};
int payload = 0;

void producer()
{
    payload = 42;
    ready.store(true, std::memory_order_release);
    ready.notify_one();
}

int consumer()
{
    ready.wait(false, std::memory_order_acquire);
    return payload;
}
```

release 存储发布 `payload`，acquire 等待读取到变化后的值并取得相应可见性。通知本身不替代值的变化和内存顺序。若值从旧值变为新值又迅速恢复，等待者可能观察不到短暂变化，因此原子等待也需要避免不恰当的 ABA 式状态编码。

原子等待适合围绕单个原子状态等待，通常不需要单独的互斥量和条件变量。条件变量适合由多个字段共同构成的谓词，并能在同一锁下原子地检查复杂状态。两者不是简单的性能替代关系。

### 6.5 内存顺序

`std::memory_order_relaxed` 只要求目标原子操作保持原子性并参与该对象的修改顺序，不为其他普通内存访问建立跨线程同步。它适合无需发布其他数据的统计计数和独立序号。

`std::memory_order_release` 用于发布操作，保证同一线程中位于其前面的相关读写不会被移到发布之后。`std::memory_order_acquire` 用于取得操作，保证位于其后的相关读写不会被移到取得之前。当 acquire 读取到对应 release 发布的值或其释放序列中的值时，两者建立同步。

`std::memory_order_acq_rel` 用于同时读取和修改的原子操作，使它兼具 acquire 与 release 约束。它适合既取得前一状态发布的数据，又向后一状态发布本次数据的读改写操作。

`std::memory_order_seq_cst` 除具备相应 acquire 或 release 语义外，还要求所有顺序一致操作表现为处于一个满足规定约束的单一全局顺序。它是默认内存顺序，推理最直接，但在部分架构和访问模式下可能需要更强指令或栅栏。

读改写操作应按照其角色选择顺序。例如只分配唯一编号的 `fetch_add` 可以使用 relaxed；用于取得引用计数之外对象内容的操作可能需要 acquire；发布最后一个初始化步骤可能需要 release；同时接收前一阶段并发布下一阶段时可能需要 acq_rel。

CAS 失败只读取当前值，因此失败顺序不能是 release 或 acq_rel。成功顺序与失败顺序的组合必须符合标准限制。内存顺序优化需要给出明确的先行发生证明；仅凭目标处理器看似按顺序运行不能构成证明。

### 6.6 同步关系

`sequenced-before` 描述同一线程内求值之间由语言规则确定的先后关系。它是构造跨线程推理的基础。

`synchronizes-with` 描述特定同步操作之间的关系，例如互斥量解锁与随后成功加锁，或者 release 原子操作与读取其发布值的 acquire 操作。

`happens-before` 由线程内先序、同步关系及其传递闭包构成。如果写操作先行发生于另一个线程的读取，后者就能按照内存模型观察受到该关系约束的结果。并发冲突的普通访问若没有这样的关系，可能形成数据竞争。

每个原子对象都有自己的修改顺序，所有对该对象的修改在其中全序排列。读取必须按照内存模型规则从某个修改取得值，但不同原子对象的修改顺序通常不能直接拼成统一时间线。

释放序列以 release 操作为起点，并按标准规则包含随后与其相连的原子读改写操作。acquire 操作读取到释放序列产生的值时，可以与序列头建立同步。这一机制使多个线程通过同一原子对象进行中继式状态推进成为可能。

### 6.7 原子同步的限制

原子操作直接保护的是被声明为原子的特定状态。两个字段各自原子，并不意味着同时读取它们可以得到同一逻辑时刻的一致快照。余额与版本、指针与长度、状态与错误码等复合不变量通常需要互斥量、单个打包状态或专门算法。

ABA 问题表示某个值从 A 变为 B 又回到 A，CAS 只比较当前位模式，因而误认为状态从未变化。常见缓解方法包括增加版本标签、使用不会快速复用地址的分配策略，以及采用危险指针、纪元回收或引用计数等安全内存回收机制。

高竞争下，CAS 循环可能反复失败，已经完成的计算被丢弃，并持续争抢同一缓存行。无锁算法保证的是某种系统级进展属性，不保证每个线程公平推进。

伪共享发生在逻辑上独立的原子变量位于同一缓存行时。不同核心分别修改它们仍会造成缓存行来回转移。可以通过数据布局、分片计数和适当对齐减少这种竞争，但对齐值应结合 `std::hardware_destructive_interference_size` 的可用性和目标平台验证。

无锁不等于高性能。复杂 CAS 循环、内存回收、缓存一致性和重试成本可能超过实现良好的互斥量。除非状态非常简单或延迟与进展属性有明确要求，否则应优先选择容易证明正确的同步结构。

## 7. 任务完成与结果同步

### 7.1 `std::future` 与 `std::promise`

`std::promise<T>` 和 `std::future<T>` 通过共享状态传递一次结果。生产者持有 promise 并设置值或异常，消费者持有 future 并等待和取得结果。共享状态独立于两个句柄对象的直接存储位置。

```cpp
#include <exception>
#include <future>
#include <stdexcept>
#include <thread>

int calculate_value(bool fail)
{
    if (fail) {
        throw std::runtime_error("calculation failed");
    }
    return 42;
}

int receive_result()
{
    std::promise<int> promise;
    std::future<int> future = promise.get_future();

    std::thread worker([promise = std::move(promise)]() mutable {
        try {
            promise.set_value(calculate_value(false));
        } catch (...) {
            promise.set_exception(std::current_exception());
        }
    });

    worker.join();
    return future.get();
}
```

`wait()` 无期限等待共享状态就绪，`wait_for()` 和 `wait_until()` 提供定时查询，返回状态可以表示已就绪、超时或延迟执行。`get()` 等待并取得值；对于普通 `future`，取得后该句柄不再具有有效共享状态。生产者在没有设置结果时销毁 promise，会使共享状态以 `broken_promise` 错误就绪，消费者的 `get()` 将抛出相应的 `std::future_error`。

异常可以通过 `set_exception(std::current_exception())` 保存，并在消费者调用 `get()` 时重新抛出。线程函数需要自行捕获异常，不能让异常越过线程入口传播。

### 7.2 `std::packaged_task`

`std::packaged_task<Signature>` 把可调用对象包装为异步结果生产者。调用 packaged task 时，可调用对象的返回值或异常被写入共享状态，调用者通过 `get_future()` 获得相应 future。

```cpp
#include <future>
#include <thread>
#include <utility>

int execute_task()
{
    std::packaged_task<int(int, int)> task(
        [](int left, int right) {
            return left + right;
        }
    );
    std::future<int> result = task.get_future();

    std::thread worker(std::move(task), 20, 22);
    worker.join();
    return result.get();
}
```

线程池可以把不同 callable 封装为统一的无参数任务，同时把每个 packaged task 对应的 future 返回给提交者。实现时需要处理移动语义、队列关闭、未执行任务的共享状态和工作线程异常。

### 7.3 `std::async`

`std::async` 创建与可调用对象关联的共享状态。`std::launch::async` 要求异步执行，通常由另一个线程推进；`std::launch::deferred` 延迟到首次等待结果时在调用等待函数的线程中执行。未显式指定策略时，实现可以在允许的策略中选择，因此不能假定任务一定立即并行执行。

```cpp
#include <future>

int compute_sum()
{
    auto left = std::async(std::launch::async, [] {
        return 20;
    });
    auto right = std::async(std::launch::async, [] {
        return 22;
    });
    return left.get() + right.get();
}
```

由 `launch::async` 产生的共享状态具有特殊生命周期规则。在关联的最后一个 future 被销毁且任务尚未完成时，销毁路径可能等待任务完成。因此，把返回的临时 future 立即丢弃，可能使原本期望并发的调用顺序阻塞执行。应保存 future，并明确安排等待位置。

`std::async` 适合数量有限、生命周期明确的独立任务。大量短任务、并发度限制和任务取消通常更适合显式线程池或执行器框架。

### 7.4 `std::shared_future`

`std::future` 只能移动，且结果通常只能由一个消费者调用一次 `get()`。`std::shared_future` 可以复制，多个线程可以等待并读取同一共享状态，`get()` 也可以重复调用。

```cpp
#include <future>
#include <thread>

void use_value(int value);

void distribute_result()
{
    std::promise<int> promise;
    std::shared_future<int> result = promise.get_future().share();

    std::thread first([result] {
        use_value(result.get());
    });
    std::thread second([result] {
        use_value(result.get());
    });

    promise.set_value(42);
    first.join();
    second.join();
}
```

其中 `use_value` 代表应用已有的只读消费函数。`shared_future` 允许并发读取共享结果，但如果结果类型本身是可变对象或引用，调用者仍需自行同步对该对象内容的修改。共享的是结果就绪状态与访问能力，不是任意对象的自动线程安全性。

## 8. 并发错误与活性问题

### 8.1 数据竞争与未定义行为

数据竞争是 C++ 并发程序中最基本的正确性错误。它不限于明显的整数递增，还可能出现在容器并发修改、对象析构与读取重叠、非原子标志轮询、引用计数错误以及发布尚未构造完成的对象等场景。

未定义行为意味着不能依靠某次测试中的实际表现推断程序语义。把优化级别降低、把变量声明为 `volatile`、插入日志或增加短暂延迟，都不能修复数据竞争。这些操作只可能改变错误出现的概率。

正确修复需要建立明确的先行发生关系。对于复合对象，所有可能冲突的访问应遵循同一同步协议。只给写入加锁而让读取无锁进行，仍会产生数据竞争；把一个字段改为原子也不会自动保护同一不变量中的其他普通字段。

### 8.2 死锁

死锁表示一组线程永久等待彼此释放资源。经典形成条件包括互斥使用、持有并等待、资源不可强制剥夺和循环等待。工程设计通常通过破坏循环等待，或避免持锁期间再请求不可控资源来预防死锁。

最直接的方法是建立全局加锁顺序。例如资源按稳定编号排序，所有路径均按编号递增取得。需要同时取得多把锁时，`std::lock` 和 `std::scoped_lock` 能够使用避免死锁的获取算法，但它们不能修复锁之外的资源循环，也不能解决程序在持锁状态下等待条件、线程结束或回调造成的环路。

定时互斥量可以使线程在超过截止时间后退出等待，从而支持降级和诊断。超时只是恢复策略，不是正确性证明；如果失败路径仍持有其他资源，或者反复立即重试，系统可能从死锁转为活锁。

死锁检测可以采用锁依赖图、运行时锁顺序检查、线程转储和看门狗。发生停滞时，应记录每个线程正在等待的锁、已经持有的锁以及调用栈。生产系统还可以监控长时间持锁与任务无进展，但自动终止线程通常不能安全恢复被破坏的共享状态。

### 8.3 活锁

活锁表示线程仍在执行，却因相互礼让或反复冲突而无法完成任务。例如两个线程同时尝试取得两把锁，失败后同时释放、同时退避固定时间并再次冲突。与死锁不同，线程状态可能持续变化，CPU 使用率也可能较高。

缓解方法包括随机或指数退避、为竞争者引入稳定优先级、使用统一的多锁算法，以及减少需要同时协调的资源。诊断活锁应观察有效完成量，而不能只观察线程是否运行。

### 8.4 线程饥饿

线程饥饿表示某个线程长期无法获得所需资源，而其他线程仍在推进。非公平互斥量、读者偏向的共享锁、不断插队的高频任务和优先级差异都可能导致饥饿。

C++ 标准同步设施通常不承诺严格的先到先服务公平性。对公平性有明确要求的系统需要采用排队锁、任务队列、批次调度或配额机制，并用最大等待时间和服务次数分布进行验证。平均吞吐量正常并不能排除个别线程饥饿。

### 8.5 优先级反转

优先级反转发生在高优先级线程等待低优先级线程持有的锁，而中优先级线程持续占用处理器，使低优先级持锁线程无法运行。结果是高优先级任务的响应时间间接受中优先级任务影响。

实时系统可以使用操作系统提供的优先级继承或优先级上限协议。一般程序还应缩短持锁时间，避免低优先级线程持锁执行阻塞操作，并减少跨优先级共享。标准 C++ 互斥量不提供统一的优先级协议接口，相关能力需要依赖目标平台。

### 8.6 虚假唤醒

条件变量等待可能在没有相应通知时返回，这称为虚假唤醒。即使实现没有产生虚假唤醒，等待者被通知后也可能因竞争而发现条件已经被其他线程消耗。

正确处理方式始终是根据谓词等待：

```cpp
std::unique_lock<std::mutex> lock(mutex);
condition.wait(lock, [&] {
    return stopped || !queue.empty();
});
```

定时等待也需要重新检查谓词，并使用统一截止时间控制总等待时长。不能把一次唤醒直接解释为业务事件已经可用。

### 8.7 通知丢失

条件变量不保存通知次数。若通知发生时没有等待者，后续等待者不会继承该通知。若程序把通知本身当作状态，就可能形成永久等待。

解决方法是把业务事实保存在受保护状态中，例如 `ready`、队列元素数量或版本号。通知只负责促使等待者重新检查状态。只要谓词已经满足，即使通知先于等待发生，等待者在持锁检查时也会直接继续。

### 8.8 ABA 问题

ABA 常见于无锁栈和空闲链表。线程甲读取头指针 A 后暂停；线程乙移除 A，操作其他节点，又把地址相同的 A 放回；线程甲的 CAS 比较成功，但链表结构或对象生命周期已经发生变化。

解决思路包括把指针与递增版本号组合比较，采用不会过早复用对象的内存回收机制，或使用危险指针、纪元回收和经过验证的无锁容器。仅把指针声明为原子类型不能解决节点已经释放或复用的问题。

### 8.9 错误的双重检查锁定

双重检查锁定试图先无锁读取单例指针，发现为空后加锁并再次检查。若指针是普通对象，无锁读取与锁内写入会产生数据竞争；在缺少正确发布语义时，其他线程还可能观察到未完成初始化的对象。

```cpp
Singleton* instance = nullptr;
std::mutex instance_mutex;

Singleton* get_instance_wrong()
{
    if (instance == nullptr) {
        std::lock_guard<std::mutex> lock(instance_mutex);
        if (instance == nullptr) {
            instance = new Singleton;
        }
    }
    return instance;
}
```

从 C++11 开始，函数局部静态对象的初始化具有线程安全保证，通常可以直接表达按需初始化：

```cpp
Singleton& get_instance()
{
    static Singleton instance;
    return instance;
}
```

需要更复杂的一次性初始化时可以使用 `std::once_flag` 与 `std::call_once`。使用原子指针和 acquire/release 也能构造正确实现，但还必须解决对象销毁、异常和内存回收，通常没有必要替代语言提供的局部静态初始化。

## 9. 同步机制比较与选择

### 9.1 `mutex` 与 `spinlock`

互斥量在竞争时可以阻塞线程，适合临界区可能较长、线程可能过度订阅或等待期间应节省 CPU 的场景。自旋锁在等待期间占用处理器，只有临界区极短、持锁线程很可能继续运行且测量结果支持时才可能有优势。

两者的差异不应简化为系统调用与无系统调用。现代互斥量通常具有快速用户态路径，并可能先短暂自旋再阻塞。选择时应比较真实实现的吞吐量、尾延迟和 CPU 消耗。

### 9.2 `mutex` 与 `atomic`

互斥量可以保护任意复合状态，使一组操作作为临界区执行，推理方式相对直接。原子操作只直接作用于特定对象，适合独立计数、标志和经过设计的状态转换。

单个原子增量通常比加锁计数更直接，但由多个字段构成的不变量不应被机械拆成多个原子。无锁算法还需要处理内存顺序、重试、公平性和对象回收。若不能清楚证明所有允许的执行都正确，应优先使用互斥量。

### 9.3 `mutex` 与 `semaphore`

互斥量表达排他所有权，取得与释放通常由同一线程完成，适合保护数据。信号量表达可消费许可，许可数量可以大于一，释放者与取得者可以不同，适合资源池、并发限流和事件计数。

二值信号量能够限制一个线程通过，但缺少互斥量的所有权纪律。用二值信号量替代互斥量可能使错误释放、重复释放和跨线程释放更难发现。应按语义选择，而不是只按计数上限选择。

### 9.4 `condition_variable` 与 `atomic::wait`

条件变量适合等待由一把锁保护的复杂谓词，能够同时检查多个字段，并在等待时释放互斥量。`atomic::wait` 适合等待单个原子值改变，状态和等待点较为紧凑，不必另设互斥量。

如果条件是队列非空或停止，并且队列本身需要锁，条件变量通常自然。若条件只是阶段编号、一次性就绪标志或轻量状态字，原子等待可能更合适。两者都要求状态发生实际变化，通知函数本身不承载业务事实。

### 9.5 `shared_mutex` 的适用条件

共享互斥量主要适合读多写少、读取临界区不太短、多个读取者可以真正并行的负载。若读取只是一次简单字段访问，普通互斥量或原子快照可能更经济。若写入频繁，读取者与写入者之间的协调成本会抵消共享收益。

还需要评估实现的公平性、写入尾延迟、缓存一致性和 NUMA 影响。读取比例高只是必要参考，不是充分条件。最终选择应由目标平台上的读写混合测试决定。

### 9.6 `latch` 与 `barrier`

`std::latch` 是一次性倒计时，适合等待一批初始化或任务完成。`std::barrier` 可重复使用，每轮参与者到齐后进入下一阶段，并可运行完成阶段函数。只需要一次汇合时，闩锁语义更简单；迭代算法与多轮流水线需要屏障。

屏障要求正确管理参与者数量。某个线程提前退出而没有 `arrive_and_drop()`，其他参与者可能永久等待。闩锁则要求总递减量与初始计数一致。

### 9.7 阻塞等待与忙等待

阻塞等待降低等待期间的 CPU 使用率，代价是调度和唤醒延迟。忙等待避免进入睡眠，代价是持续占用处理器并产生共享缓存流量。预期等待时间、处理器余量和响应时间目标共同决定选择。

短暂自旋后阻塞的混合等待在许多负载中更稳健。应用层若无法准确限制等待上界，不应采用无限忙等待。测试时应同时报告完成时间和 CPU 时间，否则只看墙钟时间可能掩盖自旋造成的资源浪费。

### 9.8 乐观同步与悲观同步

悲观同步假定冲突需要预防，先取得锁再访问状态。它适合冲突频繁、操作成本较高或失败后难以回滚的场景。

乐观同步先读取并计算，提交时用版本或 CAS 验证状态未被其他线程改变，失败后重试。它适合冲突较少、重试成本低且状态能够原子验证的场景。高竞争或长计算会放大乐观重试成本。

乐观与悲观不是固定的性能等级。数据库事务、版本化读写和无锁状态机都需要结合冲突概率、回滚成本、公平性与延迟上界评估。

### 9.9 锁粒度

粗粒度锁用一把锁保护较大范围状态，设计简单，不变量集中，缺点是无关操作也会相互阻塞。细粒度锁把状态拆分到多把锁，提高潜在并行度，也会增加锁管理、死锁预防和一致快照的复杂度。

分段锁是在两者之间折中，例如哈希表按桶组或分片加锁。它能降低热点竞争，又比每个元素单独加锁更容易管理。分段数量过少不能缓解竞争，过多则增加内存、哈希映射和跨段操作成本。

缩小锁粒度必须保持完整不变量。若一个操作跨越多个分段，就需要规定多锁顺序或设计版本化快照。优化后应测量锁竞争、缓存局部性和维护成本，不能只比较锁的数量。

### 9.10 机制选择原则

选择同步机制时可以依次检查以下问题：

1. 正确性要求：明确共享对象、冲突访问、业务不变量、生命周期和需要建立的先后关系。
2. 状态结构：单个独立状态可考虑原子操作；复合不变量通常使用互斥量；资源许可使用信号量；复杂条件等待使用条件变量。
3. 临界区长度：短且可预测的临界区才可能考虑自旋，含阻塞操作的临界区应使用可阻塞机制并重新审查锁范围。
4. 读写比例：大量可并行读取可以测试共享互斥量，写入频繁时优先评估普通互斥量或数据分片。
5. 竞争程度：低竞争时简单机制往往足够，高竞争时应先减少共享、分片状态或批量处理，而不是只更换锁类型。
6. 实时性要求：需要关注最坏等待时间、优先级反转和调度协议，平均速度不能代表实时保证。
7. 公平性要求：标准设施未必保证严格公平，需要以最大等待时间和线程级完成分布验证。
8. 平台可移植性：标准库设施通常优于平台专用接口；采用 POSIX 自旋锁、处理器指令或平台优先级协议时，应隔离实现并提供替代路径。

推荐的工程顺序是先采用语义清楚的标准设施证明正确，再通过性能分析定位实际瓶颈，最后只对确有证据的热点进行局部优化。

## 结语

C++ 并发同步的核心不是为每次访问附加某种锁，而是明确共享状态、业务不变量和跨线程先后关系。互斥量适合保护复合状态；共享互斥量服务于经过验证的读多写少负载；条件变量等待复杂谓词；信号量管理许可；闩锁和屏障完成线程汇合；future 系列传递任务结果；原子操作则用于范围明确的状态更新和低层同步协议。

正确性证明应覆盖原子性、可见性、有序性、对象生命周期和异常路径。性能优化应建立在等价语义的测试之上，并同时观察吞吐量、尾延迟、CPU 使用率、缓存行为和公平性。对大多数工程而言，先减少可变共享状态，再采用语义清楚的标准同步设施，通常比过早引入复杂无锁算法更可靠。
