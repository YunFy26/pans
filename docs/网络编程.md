# C++ 网络编程：客户端与服务端之间的数据传输

如何进行消息传递？

当通信双方处于同一进程内时，通信双方在同一个进程虚拟地址空间中。这时候双方可以通过

- 函数返回值
- 全局变量
- 让线程操作同一个对象来进行消息传递；

这种情况下，写方写入的数据，读方可以直接看到，不需要序列化，也不需要内核进行搬运。它最简单高效，但双方要自行约定对象的生命周期、并发访问与所有权，否则会出现数据竞争。

当通信双方处于同一台机器上的两个不同进程上时，由于进程默认拥有相互隔离的虚拟地址空间，一个进程不能直接读取另一个进程里的变量。这时候如果双方要进行通信，可以通过

- 共享内存（把同一物理内存映射进双方地址空间，本质上仍像在访问同一个位置）
- 管道或 FIFO（一个进程写入、另一个进程读取，由内核按字节流搬运）
- Unix 域套接字（接口类似网络套接字，但只在本机内核中传递，不走 TCP/IP）
- 也可以使用 TCP/UDP 回环地址（127.0.0.1）套接字

此时需要约定数据边界、同步与关闭语义。

那么如果通信双方分别位于不同机器上时如何通信？共享内存、管道和 Unix 域套接字都不再适用，因为机器之间既没有共享的物理内存，也没有同一个内核来帮忙搬运。对于这种情况，操作系统维护一个通信端点：套接字（socket），此时双方通信过程如下：

- 发送方把消息编码成双方约定的字节序列，通过 `send` 交给本机内核的发送缓冲区；
- 内核协议栈负责把字节送往对端机器，放入对端内核的接收缓冲区；
- 接收方再通过 `recv` 把字节取回自己的进程。

即使双方恰好位于同一台机器上，只要选择走 TCP/IP 套接字，也是同一套流程。两端能操作的始终是自己这一端的套接字和内核缓冲区。

正因如此，网络传输与直接读写内存或本机管道有本质区别。TCP 套接字对应用表现为双向字节流，一次发送可能在另一端被拆成多次读取，一次读取也可能合并多次发送的内容；UDP 套接字则按数据报交付，但可能丢失、乱序或重复。由于要双方都进行通信，所以双方需要对连接生命周期、消息边界、字段编码、关闭时机和故障处理等情况达成一致。

本文以 Linux 上的 POSIX 套接字接口为主，说明客户端与服务端之间双向传输涉及的基本概念和工程要点。除专门说明外，示例以 C++20 为编写标准。

- 本文不覆盖 Windows Winsock 的具体差异；跨平台项目应把套接字调用封装在独立层中。
- C++ 标准库截至 C++23 仍没有可移植的套接字接口，示例直接使用 POSIX API，并用 RAII 管理文件描述符。
- 正文以 TCP 为主，UDP 单独成章说明；`poll`、`epoll` 是 Linux 系统接口，不代表所有平台。
- 序列化示例使用 `<cstdint>` 的定宽类型，避免把结构体布局直接当作线上格式。

## 1. 客户端与服务端的基础模型

### 1.1 客户端与服务端的分工

服务端在启动前就应确定自己提供服务所用的地址和端口，然后创建套接字、绑定地址并进入监听状态。客户端知道服务端的地址后主动发起连接，或者向服务端的 UDP 端口发送数据报。

连接建立完成后，传输层不再区分主动方和被动方。对 TCP 而言，两端各持有一个已连接套接字，都可以读取对端发来的数据，也都可以向对端写入数据。

两端要各自维护自己发送的数据，同时能够处理对端随时发来的数据。客户端可能发送请求后等待服务端响应，也可能接收服务端主动推送的更新；服务端同样要同时管理多条连接上的输入与输出。

### 1.2 全双工与互相传输

TCP 连接是全双工的。内核为每个方向分别维护接收缓冲区和发送缓冲区：一方写入的数据进入发送缓冲区，经过网络到达对端接收缓冲区，再由对端读取。两个方向互不阻塞，一方持续发送数据的同时，另一方仍可向相反方向发送自己的数据。

全双工带来一个容易被忽略的事实：数据到达的顺序只保证单个方向内有序，服务端发送顺序与客户端发送顺序之间不存在全局排序。应用需要依靠消息中的类型、标识和时间等字段描述业务先后关系，而不是假设"我先收到客户端消息，所以我发出的响应一定排在客户端后续消息之前"。

全双工也意味着关闭可以分方向进行。一端调用 `shutdown(SHUT_WR)` 只关闭自己的发送方向，通知对端"我不会再发数据"，但仍可以继续读取对端数据。这种半关闭能力是优雅结束互相传输的基础。

### 1.3 常见的双向传输形态

不同应用对双向传输的组织方式不同，常见形态包括：

- 一次性请求响应：客户端连接后发送一个请求，服务端回复一个结果，然后任意一方关闭连接。适合简单查询，每次连接都要承担握手开销。
- 长连接上的顺序请求响应：连接保持打开，客户端发送请求后等待响应，收到响应后才发送下一个请求。逻辑简单，但一方慢速处理会阻塞同一连接上的后续请求。
- 流水线与并发请求：客户端在不等待前一个响应的情况下连续发送多个请求，通过消息 ID 把响应与请求对应起来。吞吐更高，但要求协议支持乱序完成。
- 服务端推送：连接建立后，服务端可以主动向客户端发送状态更新、通知或事件，不必等待请求。客户端需要持续读取，不能只在上一次请求后读取一次。
- 双向对等消息流：两端都可以随时发送业务消息，例如聊天、协作编辑和订阅转发。此时每端都需要独立的发送队列和读取循环。

选择哪种形态取决于业务是否允许乱序、是否需要背压、是否要求低延迟，而不是单纯看哪一方先发起连接。

### 1.4 套接字、文件描述符与内核缓冲区

`socket()` 创建套接字后，应用拿到的是一个文件描述符。文件描述符不是数据本身，而是访问内核套接字对象的句柄。内核对象保存本地地址、对端地址、协议状态、发送与接收缓冲区、等待队列等信息。

文件描述符按进程管理，可以在进程内被复制，也可以在进程间通过继承或 Unix 域套接字传递。`close()` 只减少引用计数；只有最后一个引用被关闭时，内核才会真正释放套接字。多线程程序中，两个线程分别持有同一套接字的不同描述符副本时，不能只靠其中一方关闭就认为连接一定终止。

由于描述符需要可靠释放，工程上应把原始 fd 封装到 RAII 类中。构造函数取得所有权，移动构造或移动赋值转移所有权，析构函数关闭描述符。这样异常路径、提前返回和连接结束都不容易泄漏描述符。

### 1.5 TCP 与 UDP 的选择

TCP 提供面向连接的可靠字节流：数据按发送顺序到达，重复与丢失由协议栈处理，应用收到的是无边界但有序的流。它适合请求响应、文件传输、聊天和任何要求完整可靠顺序的协议，代价是握手、确认、重传和拥塞控制带来的额外延迟与状态。

UDP 提供无连接的不可靠数据报：每次 `sendto` 对应一个数据报，但可能丢失、乱序、重复，也没有流量控制和拥塞控制。它适合对延迟敏感、能容忍少量丢失或已在应用层实现可靠性的场景，例如音视频、实时状态和局域网广播。

选择时先问三个问题：数据丢失是否可接受；消息顺序是否重要；是否需要长时间双向长连接。只要答案是需要可靠有序的长时间互传，通常应选择 TCP；只有明确需要低延迟或组播广播时，才考虑在 UDP 之上自行实现可靠性。

## 2. TCP 连接生命周期

### 2.1 地址、端口与主机名

网络地址由 IP 地址与端口号共同标识。IPv4 地址通常写作点分十进制，端口是 16 位无符号整数。客户端使用服务端 IP 与端口定位服务端，服务端通过接受连接得到对端地址；操作系统用本地地址、本地端口、对端地址、对端端口共同区分一条 TCP 连接。

端口 0 到 1023 通常需要特权，服务端常用 1024 以上的固定端口。客户端一般不显式指定本地端口，由内核从临时端口范围分配。`INADDR_ANY` 表示绑定到本机所有 IPv4 地址，适合对外提供服务的服务器；只允许本机访问时绑定 `127.0.0.1`。

数值 IP 可以用 `inet_pton` 解析，主机名和服务名应优先使用 `getaddrinfo`：

```cpp
#include <arpa/inet.h>
#include <cstdint>
#include <netinet/in.h>
#include <stdexcept>
#include <string>

sockaddr_in MakeIpv4Address(const char* ip, std::uint16_t port)
{
    sockaddr_in address{};
    address.sin_family = AF_INET;
    address.sin_port = htons(port);
    if (::inet_pton(AF_INET, ip, &address.sin_addr) != 1) {
        throw std::invalid_argument("invalid IPv4 address");
    }
    return address;
}
```

`htons` 把主机字节序转换为网络字节序，这里对应"端口号在网络上按大端传输"。解析主机名时应使用 `getaddrinfo`，它能够同时处理 IPv4、IPv6、DNS 和多地址返回；`gethostbyname` 属于旧的不可重入接口，不应在新代码中使用。

### 2.2 套接字的 RAII 管理

下面的 `Socket` 只管理文件描述符的所有权，不提供平台相关的构造逻辑：

```cpp
#include <unistd.h>

class Socket {
public:
    explicit Socket(int fd) noexcept : fd_(fd) {}

    Socket(const Socket&) = delete;
    Socket& operator=(const Socket&) = delete;

    Socket(Socket&& other) noexcept : fd_(other.fd_)
    {
        other.fd_ = -1;
    }

    Socket& operator=(Socket&& other) noexcept
    {
        if (this != &other) {
            close();
            fd_ = other.fd_;
            other.fd_ = -1;
        }
        return *this;
    }

    ~Socket()
    {
        close();
    }

    int get() const noexcept
    {
        return fd_;
    }

    void close() noexcept
    {
        if (fd_ >= 0) {
            ::close(fd_);
            fd_ = -1;
        }
    }

private:
    int fd_ = -1;
};
```

析构时 `close()` 关闭描述符，移动后源对象不再拥有任何描述符。复制被删除，避免同一 fd 被两个对象分别关闭，造成另一持有者意外失去连接。

### 2.3 服务端监听与接受连接

服务端创建监听套接字后依次执行 `bind` 和 `listen`：

```cpp
#include <cerrno>
#include <cstdint>
#include <netinet/in.h>
#include <sys/socket.h>
#include <system_error>

[[noreturn]] void ThrowLastError(const char* what)
{
    throw std::system_error(errno, std::generic_category(), what);
}

Socket MakeListeningSocket(std::uint16_t port)
{
    Socket listener(::socket(AF_INET, SOCK_STREAM, 0));
    if (listener.get() < 0) {
        ThrowLastError("socket");
    }

    const int enable = 1;
    if (::setsockopt(
            listener.get(),
            SOL_SOCKET,
            SO_REUSEADDR,
            &enable,
            sizeof(enable)) < 0) {
        ThrowLastError("setsockopt(SO_REUSEADDR)");
    }

    sockaddr_in address{};
    address.sin_family = AF_INET;
    address.sin_port = htons(port);
    address.sin_addr.s_addr = htonl(INADDR_ANY);

    if (::bind(
            listener.get(),
            reinterpret_cast<const sockaddr*>(&address),
            sizeof(address)) < 0) {
        ThrowLastError("bind");
    }
    if (::listen(listener.get(), SOMAXCONN) < 0) {
        ThrowLastError("listen");
    }
    return listener;
}
```

`bind` 指定监听地址，`listen` 使套接字进入被动监听状态并设定未完成与已完成连接队列的长度。`SO_REUSEADDR` 允许服务端在连接处于 `TIME_WAIT` 时重新绑定同一端口，这对重启服务端很重要。

接受连接要调用 `accept`，它从已完成连接队列中取出一条连接，返回一个全新的已连接套接字：

```cpp
Socket AcceptConnection(Socket& listener)
{
    for (;;) {
        sockaddr_in peer{};
        socklen_t peer_size = sizeof(peer);
        const int fd = ::accept(
            listener.get(),
            reinterpret_cast<sockaddr*>(&peer),
            &peer_size);
        if (fd >= 0) {
            return Socket(fd);
        }
        if (errno == EINTR) {
            continue;
        }
        ThrowLastError("accept");
    }
}
```

监听套接字与已连接套接字是两类描述符：监听套接字从不承载应用数据，只负责接受新连接；每个已连接套接字对应一对客户端与服务端端点。如果服务端意外关闭监听套接字，已有连接不受影响，但新连接无法建立。

### 2.4 客户端主动连接

客户端创建流套接字并调用 `connect`：

```cpp
Socket ConnectTo(const char* ip, std::uint16_t port)
{
    Socket connection(::socket(AF_INET, SOCK_STREAM, 0));
    if (connection.get() < 0) {
        ThrowLastError("socket");
    }

    const sockaddr_in server = MakeIpv4Address(ip, port);
    if (::connect(
            connection.get(),
            reinterpret_cast<const sockaddr*>(&server),
            sizeof(server)) < 0) {
        ThrowLastError("connect");
    }
    return connection;
}
```

阻塞 `connect` 要等 TCP 握手完成才返回。连接不可达或服务端不响应时，失败可能很晚才出现；需要快速失败或自定义超时时，应使用非阻塞连接：先把套接字设为非阻塞，调用 `connect` 得到 `EINPROGRESS`，再用 `poll` 等待可写并检查 `SO_ERROR`。

`ECONNREFUSED` 表示对端没有进程监听该端口；`ETIMEDOUT` 通常表示握手阶段对端无响应；`EHOSTUNREACH`、`ENETUNREACH` 表示路由不可达。客户端应根据错误区分重试、切换地址和直接报错。

### 2.5 连接建立后的双向通道

TCP 三次握手完成后，两端各自拥有一个处于 `ESTABLISHED` 状态的连接套接字。对应用而言，客户端连接与 `accept` 返回的服务端连接是对称的双向通道：服务端不需要再向客户端"连接回来"，客户端也不拥有监听套接字。

这时互相传输的双方需要分别维护自己的读写流程。客户端发送请求后，服务端的 `recv` 返回请求内容；服务端发送响应后，客户端的 `recv` 返回响应内容。任何一端的读取循环都不能假设对端会立即回复，也不能在等待响应期间完全停止处理其他消息。

内核为每个方向单独计数与缓冲，因此一端关闭自己的发送方向后，另一端仍能向关闭方发送数据。应用协议可以充分利用这一语义：发送完毕用 `shutdown(SHUT_WR)` 表示"请求结束"，随后继续读取响应。

### 2.6 关闭、半关闭与连接复位

`close(fd)` 关闭文件描述符，但它既不等待对方确认，也不强制保证已经排队的发送数据被完整送达。它只表示当前持有者不再使用这个 fd；如果发送缓冲区中还有数据，内核通常仍会继续尝试发送，但应用无法再知道结果。

`shutdown(fd, SHUT_WR)` 表示"我的发送方向结束"，向对端发送 FIN；对端随后会先读到已经到达的数据，再在 `recv` 时得到 0。关闭发送方向后，本端仍可以读取对端数据。半关闭适合这样的场景：客户端发送完请求后先关闭发送方向，服务端据此知道请求完整，随后服务端仍可把结果发给客户端。

`shutdown(fd, SHUT_RD)` 停止接收方向，之后本端不会再有可读数据；`shutdown(fd, SHUT_RDWR)` 同时关闭两个方向，但不等同于立即复位。多数应用只需要 `SHUT_WR` 和最终的 `close`。

对端崩溃、向已关闭的连接继续发送、或双方同时关闭时，可能产生 `ECONNRESET` 与 RST。收到 RST 的一方后续 `recv` 返回 `ECONNRESET`，`send` 则可能产生 `EPIPE` 或 `SIGPIPE`。RST 不表示"还有机会恢复"，应当把该连接视为不可用并释放其资源。

`SO_LINGER` 可以改变关闭行为，但它不是通用的优雅关闭开关。设置 `l_onoff` 为 1、`l_linger` 为 0 时，`close` 会丢弃发送缓冲区并立即关闭，可能让对端看到 RST。工程上不应依赖它清理应用数据；需要确保数据送达时，应在应用层完成确认，再关闭连接。

## 3. 数据读写语义

### 3.1 读写函数与返回值

Linux 上可以用 `read`/`write` 操作套接字，也可以用 `recv`/`send`。套接字专用函数支持标志位，例如 `MSG_NOSIGNAL`、`MSG_PEEK`，因此网络代码通常直接使用 `recv` 与 `send`。阻塞套接字上的返回值需要仔细区分：

- 返回正数：本次传输的实际字节数。对字节流套接字，它可能小于调用者请求的长度。
- `recv` 返回 0：对端已经有序关闭其发送方向（收到 FIN），本端没有更多数据。这是正常结束，不是错误。
- `send` 对长度为 0 的缓冲区可能返回 0；在 `length > 0` 的阻塞调用中不应把它当作连接结束。
- 返回 -1：出错。`EINTR` 表示被信号中断，通常应重试；`EAGAIN`/`EWOULDBLOCK` 表示非阻塞套接字暂时无法完成。

对字节流套接字，调用 `recv(fd, buffer, 4096)` 只保证"至少返回一个字节或 0/-1"，不保证填满 4096 字节。如果发送端一次写入 2000 字节，接收端可能一次读回 2000、分成两次 1000、甚至出现其他任意拆分。

### 3.2 部分发送与完整发送

`send` 成功只表示数据已经进入本端内核发送缓冲区，不表示对端已经收到，更不表示对端应用已经处理。它还可能只发送请求长度的一部分，例如发送缓冲区剩余空间不足或写操作被信号中断。应用必须循环发送，直到完整写入所需字节：

```cpp
#include <cerrno>
#include <cstddef>
#include <sys/socket.h>

void WriteAll(int fd, const char* data, std::size_t length)
{
    while (length > 0) {
        const ssize_t written = ::send(
            fd,
            data,
            length,
            MSG_NOSIGNAL);
        if (written > 0) {
            data += written;
            length -= static_cast<std::size_t>(written);
            continue;
        }
        if (written < 0 && errno == EINTR) {
            continue;
        }
        ThrowLastError("send");
    }
}
```

`MSG_NOSIGNAL` 阻止写已关闭连接时进程收到 `SIGPIPE`，错误会以 `EPIPE` 形式返回。`WriteAll` 只适用于阻塞套接字；非阻塞套接字在缓冲区满时应暂停发送并注册可写事件，而不是在循环中空转。

### 3.3 部分接收与完整接收

接收端同样不能假定一次 `recv` 就得到一帧完整数据。长度前缀协议读取帧头后，还需要继续读取剩余正文，直到凑齐声明的长度：

```cpp
#include <cerrno>
#include <cstddef>
#include <stdexcept>
#include <sys/socket.h>

void ReadAll(int fd, char* data, std::size_t length)
{
    while (length > 0) {
        const ssize_t received = ::recv(fd, data, length, 0);
        if (received > 0) {
            data += received;
            length -= static_cast<std::size_t>(received);
            continue;
        }
        if (received == 0) {
            throw std::runtime_error(
                "connection closed before full message");
        }
        if (errno == EINTR) {
            continue;
        }
        ThrowLastError("recv");
    }
}
```

连接中途 EOF 表示对端在完整消息送达前关闭了发送方向，这通常是协议错误或连接故障。调用方应向上抛出错误并结束连接，而不是无限等待缺失的字节。

### 3.4 TCP 是字节流：没有消息边界

TCP 只保证字节顺序，不保留应用层的消息边界。发送端连续执行两次 `send`，接收端可能一次 `recv` 就收到两段内容；发送端一次 `send` 的内容，接收端也可能分多次读取。这与管道类似：传输层不知道什么是"一条消息"。

因此，互相传输的双方必须自己定义消息边界。常见做法有固定长度消息、长度前缀、分隔符加转义、或者像 HTTP 那样用头字段描述正文长度。边界规则属于应用协议的一部分，两端必须完全一致，否则会出现粘包、拆包和解析错位。

### 3.5 内核缓冲区与背压

发送端写入的数据先进入发送缓冲区，接收端读取的是本端接收缓冲区中的数据。接收缓冲区满时，TCP 通过窗口机制让发送端停止发送，发送缓冲区随后变满，应用层的 `send` 开始阻塞或返回 `EAGAIN`。这种逐级传导称为背压，它让慢消费方最终限制快生产方。

因此，`send` 阻塞或非阻塞写满并不意味着网络错误，而是对端消费速度跟不上。服务端应利用背压决定何时丢弃、拒绝或排队数据，不应为了"提高发送效率"无限扩大缓冲区，否则内存会被慢速连接耗尽。

`SO_SNDBUF` 与 `SO_RCVBUF` 可以调整内核缓冲区，但实际生效值可能由内核加倍或受系统上限约束。应用层通常不需要频繁修改它们，更需要关注单条连接的发送队列上限与整体内存预算。

### 3.6 Nagle 算法与 TCP_NODELAY

Nagle 算法合并小的发送数据以减少网络报文数量，但也可能让小的交互式消息等待之前未确认的数据，形成额外延迟。TCP 默认启用 Nagle，而许多客户端服务端协议由许多短消息组成，这类应用应设置 `TCP_NODELAY`：

```cpp
#include <netinet/tcp.h>

void DisableNagle(int fd)
{
    const int enable = 1;
    if (::setsockopt(
            fd,
            IPPROTO_TCP,
            TCP_NODELAY,
            &enable,
            sizeof(enable)) < 0) {
        ThrowLastError("setsockopt(TCP_NODELAY)");
    }
}
```

`TCP_NODELAY` 关闭 Nagle，不等于应该为每条小消息单独调用 `send`。更好的做法是在应用层合并可合并的消息、按帧批量写入，再配合适当确认策略，避免把性能问题转嫁给底层。

### 3.7 SIGPIPE 与 EPIPE

向已经收到 RST 或对端已关闭的连接写入时，系统可能发送 `SIGPIPE`。默认行为是终止整个进程，这对服务端尤其危险：单个连接的数据竞争错误可能让服务进程退出。

处理方式有两种：统一忽略 `SIGPIPE`，然后从 `send` 的 `EPIPE` 错误中识别连接已坏；或在每次 `send` 时使用 `MSG_NOSIGNAL`。选择哪种取决于代码风格，但必须全项目一致。事件驱动服务端尤其要避免因写一个已经断开的连接而终止所有连接。

## 4. 消息帧与编码

### 4.1 协议要回答的问题

套接字只负责搬运字节或数据报，业务语义由应用协议定义。协议至少要回答以下问题：

- 一条消息从哪里开始、到哪里结束；
- 各字段采用什么字节顺序和宽度；
- 字段是定长还是变长，变长部分如何表示长度；
- 是否允许空消息、可选字段和未来版本；
- 请求与响应如何对应，服务端推送如何与业务事件关联；
- 对端发来过长、过短或字段非法的消息时如何处理；
- 连接结束后，未完成的请求和消息如何判定结果。

双方只有在这些问题上保持一致，才能在"互相传输"时正确解释对方的数据。协议正确性通常比单一函数的发送效率更重要。

### 4.2 帧格式的选择

固定长度帧实现最简单，每条消息占相同字节数，接收方读够长度即可解析。它适合字段数量与内容大小稳定的协议，字段扩展会导致整条消息重新设计。

长度前缀帧在每个消息前携带本消息的长度，接收方先读长度，再按长度读取正文。它适合长度变化大、且需要在读取正文前检查大小上限的场景，是二进制协议中最常用的形式。

分隔符帧以特殊字节或字节序列结束，例如换行符，常见于文本协议。正文中不能自然出现分隔符，否则需要转义，或者改用长度前缀。

自描述帧通常由类型、版本、长度和若干字段组成，例如 TLV（类型-长度-值）。它便于增量扩展，但每层头字段都会增加解析复杂度，也不应把嵌套结构无限制加深。

### 4.3 长度前缀帧

下面使用 9 字节头：`kind` 占 1 字节、`id` 占 4 字节、`payload` 长度占 4 字节：

```text
 0        1  2              5  6              9
+----------+----------------+----------------+----------------+
|  kind(1) |     id(4)      |   length(4)    |     payload    |
+----------+----------------+----------------+----------------+
```

长度字段按网络字节序即大端存放，确保不同字节序主机得到一致结果：

```cpp
#include <cstdint>
#include <limits>
#include <stdexcept>
#include <string>
#include <vector>

constexpr std::size_t kHeaderSize = 9;
constexpr std::uint32_t kMaxPayloadSize = 1u << 20;

void PutU32(std::vector<std::uint8_t>& bytes, std::uint32_t value)
{
    bytes.push_back(static_cast<std::uint8_t>(value >> 24));
    bytes.push_back(static_cast<std::uint8_t>(value >> 16));
    bytes.push_back(static_cast<std::uint8_t>(value >> 8));
    bytes.push_back(static_cast<std::uint8_t>(value));
}

std::uint32_t GetU32(const std::uint8_t* data)
{
    return (static_cast<std::uint32_t>(data[0]) << 24) |
           (static_cast<std::uint32_t>(data[1]) << 16) |
           (static_cast<std::uint32_t>(data[2]) << 8) |
           static_cast<std::uint32_t>(data[3]);
}

struct Message {
    std::uint8_t kind = 0;
    std::uint32_t id = 0;
    `std::string` payload;
};

std::vector<std::uint8_t> SerializeMessage(const Message& message)
{
    if (message.payload.size() >
        static_cast<std::size_t>(std::numeric_limits<std::uint32_t>::max())) {
        throw std::length_error("payload too large");
    }

    std::vector<std::uint8_t> bytes;
    bytes.reserve(kHeaderSize + message.payload.size());
    bytes.push_back(message.kind);
    PutU32(bytes, message.id);
    PutU32(bytes, static_cast<std::uint32_t>(message.payload.size()));
    bytes.insert(bytes.end(), message.payload.begin(), message.payload.end());
    return bytes;
}
```

`DeserializeMessage` 先检查帧头是否完整，再检查声明长度是否超过上限，最后确认整帧字节数与声明长度一致：

```cpp
Message DeserializeMessage(const std::uint8_t* data, std::size_t size)
{
    if (size < kHeaderSize) {
        throw std::runtime_error("short frame");
    }

    const std::uint32_t declared = GetU32(data + 5);
    if (declared > kMaxPayloadSize) {
        throw std::runtime_error("payload too large");
    }

    const std::size_t payload_size = static_cast<std::size_t>(declared);
    if (size != kHeaderSize + payload_size) {
        throw std::runtime_error("frame length mismatch");
    }

    Message message;
    message.kind = data[0];
    message.id = GetU32(data + 1);
    message.payload.assign(
        reinterpret_cast<const char*>(data + kHeaderSize),
        payload_size);
    return message;
}
```

完整接收一帧时，先读取 9 字节头部，读取正文前就检查长度：

```cpp
#include <cstring>

std::vector<std::uint8_t> ReadFrame(int fd)
{
    std::uint8_t header[kHeaderSize];
    ReadAll(fd, reinterpret_cast<char*>(header), kHeaderSize);

    const std::uint32_t declared = GetU32(header + 5);
    if (declared > kMaxPayloadSize) {
        throw std::runtime_error("payload too large");
    }

    const std::size_t payload_size = static_cast<std::size_t>(declared);
    std::vector<std::uint8_t> frame(kHeaderSize + payload_size);
    std::memcpy(frame.data(), header, kHeaderSize);
    if (payload_size != 0) {
        ReadAll(
            fd,
            reinterpret_cast<char*>(frame.data() + kHeaderSize),
            payload_size);
    }
    return frame;
}
```

必须把"声明长度"与"已接收字节数"分开：先读头部后，对端可能正好只发来半帧。若正文还没有到齐，应保留已读部分并继续接收，不能因为一次 `recv` 不足就丢弃数据。

### 4.4 显式序列化而不是结构体直投

新手常把本地结构体指针直接转成字节发送：

```cpp
// 不推荐：结构体布局不是稳定、可移植的线上格式
::send(fd, &request, sizeof(request), MSG_NOSIGNAL);
```

这种做法依赖本机编译器的成员顺序、结构体对齐与填充、`sizeof`、整数宽度和字节序。同一份代码在不同编译器、不同 ABI、不同处理器上可能生成不同的字节序列，进程内与跨主机传输的含义也不同。即使使用 `#pragma pack`，仍然无法解决字节序和平台整数宽度问题。

正确做法是逐字段显式编码：定宽整数按确定字节序写入，字符串与字节序列先写长度再写内容，枚举与布尔值编码为明确整数。结构体可以只在解析完成后的内存中使用，例如用 `id`、`kind` 等字段构造本地对象，但不能把本地对象的内存当作线上格式。

### 4.5 大小限制与恶意输入

网络对端应被视为不可信输入。长度字段如果来自远端，必须先与上限比较再分配内存、控制循环次数和拷贝大小。下面的顺序是错误的：

```cpp
// 错误：未检查长度就分配，恶意对端可以触发巨大分配或内存耗尽
std::vector<std::uint8_t> body(declared_length);
ReadAll(fd, reinterpret_cast<char*>(body.data()), body.size());
```

上限应根据业务需要设定，例如请求正文不超过 1 MiB、响应不超过 16 MiB。超过上限应关闭连接或按协议返回错误，而不是继续读取可能永远到不了的超长正文。

解析时还要防止把有符号整数与无符号长度混用，防止"头长度 + 正文长度"溢出。帧的头部本身是否计入长度、空消息是否合法、长度为零的正文表示什么，都应在协议文档中写明，并在解析时保持一致。

### 4.6 请求与响应对应、推送消息

长连接允许同时存在多个未完成的请求，但响应到达顺序不一定与请求发送顺序相同。为了让双方能对应，每条消息可带单调递增的消息 ID。客户端发送请求时记录 ID 与回调或待完成条目，服务端把请求 ID 原样复制到响应中，客户端据此分发。

服务端主动推送不针对某个请求，因此推送消息应使用独立的消息类型，携带事件标识或序号，并遵守与请求相同的帧格式。客户端收到推送后不能把它误当作某个请求的响应，否则复用连接时会出现消息错配。

如果客户端因超时重发同一请求，服务端可能已经处理过第一个请求，只是响应丢失。此时需要业务层面的幂等键或去重机制；传输层的重发并不能保证"只执行一次"。消息 ID 用于关联，幂等语义属于业务协议的一部分。

## 5. UDP 传输

### 5.1 UDP 语义

UDP 套接字以数据报为单位传输。每次 `sendto` 发送一个数据报，每次 `recvfrom` 读取一个完整数据报。数据报之间不存在 TCP 那样的字节流合并，也不会被接收端拆成半个数据报返回。

作为代价，UDP 不保证交付、顺序与不重复：报文可能丢失、乱序到达，也可能在极少数情况下重复。应用必须接受这些情况，或者自己实现确认、序号、重传和去重。UDP 也没有连接状态和拥塞控制，发送速率不受对端接收能力约束，长时间高速发送可能造成丢包。

### 5.2 服务端收发与回复

服务端创建 `SOCK_DGRAM` 套接字并绑定端口，不需要 `listen` 和 `accept`。收到数据报时，`recvfrom` 会返回发送方地址；回复时必须把该地址传回 `sendto`，否则客户端无法收到：

```cpp
#include <array>
#include <cerrno>
#include <cstdint>
#include <netinet/in.h>
#include <sys/socket.h>

Socket MakeUdpSocket(std::uint16_t port)
{
    Socket udp(::socket(AF_INET, SOCK_DGRAM, 0));
    if (udp.get() < 0) {
        ThrowLastError("socket");
    }

    sockaddr_in address{};
    address.sin_family = AF_INET;
    address.sin_port = htons(port);
    address.sin_addr.s_addr = htonl(INADDR_ANY);
    if (::bind(
            udp.get(),
            reinterpret_cast<const sockaddr*>(&address),
            sizeof(address)) < 0) {
        ThrowLastError("bind");
    }
    return udp;
}

void RunUdpEcho(std::uint16_t port)
{
    Socket server = MakeUdpSocket(port);
    std::array<char, 2048> buffer{};

    for (;;) {
        sockaddr_in peer{};
        socklen_t peer_size = sizeof(peer);
        const ssize_t received = ::recvfrom(
            server.get(),
            buffer.data(),
            buffer.size(),
            0,
            reinterpret_cast<sockaddr*>(&peer),
            &peer_size);
        if (received < 0) {
            if (errno == EINTR) {
                continue;
            }
            ThrowLastError("recvfrom");
        }

        const std::size_t length = static_cast<std::size_t>(received);
        const ssize_t sent = ::sendto(
            server.get(),
            buffer.data(),
            length,
            0,
            reinterpret_cast<const sockaddr*>(&peer),
            peer_size);
        if (sent < 0) {
            if (errno == EINTR) {
                continue;
            }
            ThrowLastError("sendto");
        }
    }
}
```

UDP 是消息有界的：一个 `recvfrom` 恰好对应发送端一个 `sendto`。但如果接收缓冲区小于数据报长度，内核会截断多余部分，应用只能得到数据报前部。Linux 上可以用 `MSG_TRUNC` 标志在 `recvmsg` 中检测是否被截断，而不是把截断后的短数据当作完整消息。

### 5.3 客户端收发与超时

客户端同样创建 `SOCK_DGRAM` 套接字。未绑定的 UDP 套接字在第一次发送时由内核自动分配临时端口，之后可以用 `sendto` 向不同服务端发送，用 `recvfrom` 接收任意来源的数据报。

UDP 的请求响应需要应用自己处理超时。可以用 `SO_RCVTIMEO` 让阻塞 `recvfrom` 限时返回，超时后 `errno` 为 `EAGAIN`/`EWOULDBLOCK`：

```cpp
#include <sys/time.h>

void SetReceiveTimeout(int fd, int seconds)
{
    timeval timeout{seconds, 0};
    if (::setsockopt(
            fd,
            SOL_SOCKET,
            SO_RCVTIMEO,
            &timeout,
            sizeof(timeout)) < 0) {
        ThrowLastError("setsockopt(SO_RCVTIMEO)");
    }
}
```

仅设置一次超时还不够：如果服务端回复较慢但最终可达，客户端可能需要多次重试；如果中间出现乱序，较早到达的旧响应也应能够识别。可靠的 UDP 请求响应通常要携带消息 ID、序号或时间戳。

### 5.4 connect 后的 UDP

UDP 套接字也可以调用 `connect`，但这里的 `connect` 不发送任何数据报，只是记录默认对端地址并让内核过滤来源。此后可以改用 `send` 与 `recv`，并且内核只接受该对端地址发来的数据报，返回的 ICMP 端口不可达错误也更容易同步给应用。

`connect` 适合每次会话只与一个服务端通信的客户端：代码更简单，也避免把其他主机的数据报误当作响应。服务端需要同时服务多个客户端时通常不 `connect`，而是每次用 `recvfrom` 取得来源并用 `sendto` 回复。

### 5.5 可靠性与消息大小

UDP 负载上限由协议决定。IPv4 UDP 数据报理论负载最大约 65507 字节，但超过路径 MTU 的数据报可能被 IP 分片，分片丢失会使整个数据报无法重组。局域网内常用不超过 1472 字节（Ethernet MTU 1500 减 IP 与 UDP 头部）作为保守选择；跨公网还应考虑更小 MTU、隧道与路径探测结果。

真正需要可靠性的协议应在应用层增加：

- 序号，用于检测乱序与重复；
- 确认与重传，用于发现并恢复丢失；
- 超时与重试上限，防止永久等待；
- 去重与幂等，防止重复处理；
- 流量与速率控制，防止发送端压垮接收端或网络。

这些机制 TCP 已经提供。只有在组播、广播、实时性要求或自研协议确实带来明显收益时，才值得在 UDP 之上重新实现。

## 6. 阻塞、非阻塞与多路复用

### 6.1 阻塞模型与每连接一线程

阻塞套接字上，`recv` 没有数据时会让线程等待，`send` 缓冲区满时也会等待。最简单的高并发服务端模型是每连接一个线程：主线程 `accept` 后把连接交给新线程，线程在阻塞 `recv` 上等待并处理该连接。程序结构接近顺序代码，容易理解。

该模型的成本是每连接一个线程栈、一次上下文切换和锁竞争。连接数达到数千或大量连接长期空闲时，线程开销与调度成本会变得显著。它仍然适合连接数少、单连接处理较重的服务，例如每个客户端长期执行计算或独立业务。

### 6.2 非阻塞套接字

把套接字设为 `O_NONBLOCK` 后，读写不会让线程无限等待：

```cpp
#include <fcntl.h>

void SetNonBlocking(int fd)
{
    const int flags = ::fcntl(fd, F_GETFL, 0);
    if (flags < 0) {
        ThrowLastError("fcntl(F_GETFL)");
    }
    if (::fcntl(fd, F_SETFL, flags | O_NONBLOCK) < 0) {
        ThrowLastError("fcntl(F_SETFL)");
    }
}
```

非阻塞套接字上，`recv` 没有可读数据或 `send` 缓冲区已满时返回 -1，`errno` 为 `EAGAIN`/`EWOULDBLOCK`。这是"现在不能完成，请稍后再试"，不是连接错误。调用者必须把这一状态转化为事件驱动逻辑，而不是在循环中立即重试，否则会形成忙等并占满 CPU。

非阻塞套接字返回的其他错误仍需要处理：`ECONNRESET` 表示连接被复位，`EPIPE` 表示对端已关闭。`recv` 返回 0 仍然表示对端有序关闭发送方向。

### 6.3 `poll` 与 `select`

`select` 和 `poll` 都让一个线程同时等待多个描述符。`select` 受限于 `FD_SETSIZE`，每次调用需要重建描述符集合，复杂度随描述符数量增长。`poll` 使用动态数组表达兴趣事件，没有 `select` 的集合上限，接口也更接近事件模型，但每次调用仍要遍历传入的描述符数组。

`pollfd` 中的 `events` 表示调用者关心的事件，`revents` 由内核填写实际发生的事件：

- `POLLIN`：有数据可读，或对端已关闭发送方向（需要进一步 `recv` 区分）；
- `POLLOUT`：可以写入；
- `POLLERR`：套接字发生错误；
- `POLLHUP`：连接挂断；
- `POLLNVAL`：描述符未打开或非法。

`POLLIN` 不直接告诉应用是普通数据还是 EOF，必须调用 `recv`：返回正数是数据，返回 0 是 EOF，返回 -1 是错误。同样，`POLLERR` 发生后通常需要通过 `getsockopt(SO_ERROR)` 取得具体错误码。

### 6.4 `epoll`

Linux 提供 `epoll` 作为大批量连接下的多路复用接口。`epoll_create1` 创建实例，`epoll_ctl` 增删改关注事件，`epoll_wait` 返回就绪事件。与 `poll` 每次传入全部描述符不同，注册后内核维护关注集合，`epoll_wait` 只返回状态发生变化或持续就绪的描述符。

一个典型事件循环会同时注册监听套接字和全部已连接套接字：

- 监听套接字可读时循环 `accept`，把新连接设为非阻塞并注册到 epoll；
- 连接套接字可读时读取数据并交给协议解析；
- 连接套接字可写时发送应用层排队的数据；
- `EPOLLRDHUP`、`EPOLLHUP`、`EPOLLERR` 或读取错误时关闭连接并清理状态。

`epoll_wait` 返回的事件数量可能小于就绪总数，返回 0 表示超时，-1 且 `EINTR` 表示被信号中断。每次 `epoll_wait` 后不能假设只处理返回的几个事件，也不能假设下一次调用不会再返回相同事件。

### 6.5 水平触发与边缘触发

epoll 默认水平触发：只要条件仍然满足，每次 `epoll_wait` 都可能返回该描述符。对可读事件，未读完的数据会在下一次调用继续触发；对可写事件，只要缓冲区可写就一直触发。水平触发编程简单，但可写事件必须小心处理，否则会不断唤醒。

边缘触发只在状态从不可用变为可用时通知一次，要求应用把可读数据读到 `EAGAIN`、把可写数据处理到清空队列，否则会漏掉数据。边缘触发减少重复唤醒，但代码更容易出错，通常还需要一个完整的应用层读写缓冲模型支撑。

无论采用哪种触发模式，都不能把"事件到来"当作"一整条消息已经到达"。TCP 事件只表示有字节可读，消息是否完整仍要由帧解析器判断。对可读事件的最佳实践是持续读取并增量解析，直到 `EAGAIN`，把解析出的完整帧交给业务处理。

### 6.6 接收缓冲区的增量解析

事件循环中不应为每条消息分配与释放大量临时缓冲，也不应在 `recv` 后把未完整的半帧直接交给业务层。可以维护每条连接的应用层接收缓冲：

```cpp
#include <cstdint>
#include <optional>
#include <vector>

class FrameReader {
public:
    void append(const std::uint8_t* data, std::size_t length)
    {
        buffer_.insert(buffer_.end(), data, data + length);
    }

    std::optional<std::vector<std::uint8_t>> take_frame()
    {
        if (buffer_.size() < kHeaderSize) {
            return std::nullopt;
        }

        const std::size_t payload_size =
            static_cast<std::size_t>(GetU32(buffer_.data() + 5));
        if (payload_size > kMaxPayloadSize) {
            throw std::runtime_error("payload too large");
        }

        const std::size_t total = kHeaderSize + payload_size;
        if (buffer_.size() < total) {
            return std::nullopt;
        }

        std::vector<std::uint8_t> frame(
            buffer_.begin(),
            buffer_.begin() + static_cast<std::ptrdiff_t>(total));
        buffer_.erase(
            buffer_.begin(),
            buffer_.begin() + static_cast<std::ptrdiff_t>(total));
        return frame;
    }

private:
    std::vector<std::uint8_t> buffer_;
};
```

`buffer_.erase` 会让剩余字节向前搬移。数据量大时可以改用 `offset` 记录已消费位置，定期压缩，或用环形缓冲区减少拷贝；正确性上，关键是任何时刻都能把"半帧残留"安全地留给下一次读取。

每次读事件处理可以概括为：把 `recv` 得到的字节追加进 `FrameReader`，然后循环 `take_frame()`，直到返回 `std::nullopt`；每个完整帧交给业务处理。这样无论 TCP 如何拆分与合并，业务层看到的始终是完整消息。

### 6.7 事件循环中的发送与背压

事件循环里不应直接循环 `send` 到缓冲区满为止，而应为每条连接维护应用层发送队列。`send` 成功时从队头推进；返回 `EAGAIN` 时停止发送并让内核关注 `EPOLLOUT`；`EPOLLOUT` 到达后继续发送队列，直到队列清空后取消写关注。

队列长度需要上限。如果对端长期不读取，队列会无限增长并耗尽内存。达到上限时应执行应用策略：丢弃最旧消息、拒绝新消息、关闭连接，或暂停产生数据的业务。这个上限就是应用层背压边界，比内核发送缓冲区大小更能反映业务可接受的内存占用。

同一时刻只应有一个线程向同一套接字写入。多个线程直接 `send` 时，可能把一条逻辑消息拆成几段交叉写入，对端会解析出混乱的帧。可行的做法包括：单事件循环内完成所有写；每个连接只由一个写线程负责；或在整个逻辑消息序列化完成后，用锁保护一次完整的 `send`。

## 7. 服务端并发模型与套接字所有权

### 7.1 三种并发模型的取舍

服务端通常在三类模型中取舍。每连接一线程用阻塞读写，简单直观，适合连接数少、业务处理集中在连接线程内的服务；线程数量受系统资源限制，成千上万个空闲连接会浪费大量内存与调度时间。

单线程事件循环用非阻塞套接字和 `poll`/`epoll` 管理所有连接，一个线程可以服务数万连接。它把并发单位从线程变成事件，代价是回调式代码更难维护，任何阻塞操作（磁盘 I/O、锁、长计算）都会阻塞所有连接，因此 CPU 密集处理需要移出事件线程。

混合模型让少数事件线程负责 `accept`、读写和协议解析，把解析出的业务任务交给固定大小的工作线程池执行。工作线程只操作任务对象，不直接访问套接字；处理完成后再把结果交还给事件线程发送。混合模型适合"大量连接 + 每请求有较重业务"的服务，但需要设计清晰的跨线程交接，不能直接在工作线程中阻塞式读写同一套接字。

选择模型应以连接数量、每个连接是否长期空闲、单条消息处理成本、代码可维护性为依据。先实现语义清晰的简单模型，再在压力测试中确认瓶颈，通常比一开始就构造复杂事件循环更可靠。

### 7.2 套接字的所有权与线程安全

文件描述符是进程共享的句柄，但套接字对象内部的读写位置、缓冲区和关闭状态不能让多个线程任意操作。最基本的所有权规则是：

- 同一连接同一时刻只有一个读取者；
- 同一连接同一时刻只有一个写入者；
- 关闭连接前必须与读写方同步，不能让 `close` 与 `recv`/`send` 并发进行。

连接结束后，如果读写线程仍持有 fd，可能出现已关闭描述符被另一个连接复用、旧线程的 `recv` 误读新连接数据的问题。避免这种竞态的方法是让套接字拥有明确的所有者：连接对象只属于事件循环或连接线程，其他线程通过消息队列与它交互；需要跨线程关闭时，应提交"关闭连接"任务而不是直接调用 `close`。

每个连接通常还需要一个连接状态对象，保存对端地址、接收缓冲、发送队列、消息 ID、最近活动时间等。对象内的方法默认由所有者串行调用，不需要为每个字段分别加锁。若多个工作线程共享连接状态，应复制出不可变快照或使用互斥量保护完整业务语义，而不是分别锁住个别字段。

### 7.3 服务端资源控制

服务端面对的是不可信且数量不受控的客户端，必须主动限制资源：

- 设定最大连接数，超过后直接拒绝或关闭最老的空闲连接；
- 为每条连接设定接收缓冲与发送队列上限，防止慢速客户端耗尽内存；
- 为读写和完整请求设定超时，防止空连接永久占位；
- 对新建连接速率限流，防止瞬时连接风暴耗尽描述符；
- 监控 `accept` 返回 `EMFILE`/`ENFILE` 的情况，这时应先释放部分空闲连接，而不是在错误上忙等。

`listen` 的 backlog 只影响内核为尚未 `accept` 的连接排队，不能缓解已接受连接上的处理压力。连接一旦被 `accept`，就进入应用自己的资源预算范围，内存、线程、任务队列和超时都应由应用管理。

## 8. 连接故障与可靠性设计

### 8.1 EOF、RST 与超时

`recv` 返回 0 表示收到 FIN，即对端应用调用了 `close` 或 `shutdown(SHUT_WR)`，且本端接收缓冲区已经读完。正常关闭应当走这条路。业务上应把"收到 EOF"当作对端不再发送的确定事实，但还不能据此断定对端已经处理完我们发送的所有数据。

`ECONNRESET` 表示连接被 RST 复位，常见原因包括对端进程崩溃、对端收到未预期的数据后关闭、主机重启或网络设备丢弃带错误状态的数据包。RST 意味着连接状态不可信，之前已发送但未确认的数据是否被处理也无法判断。

超时则代表"在预期时间内没有进展"，可能由网络拥塞、对端过慢、半开连接或路由问题造成。应用层超时不是连接状态的直接报告，它只说明本端放弃了等待；超时后应关闭连接并清理该连接上的未完成请求，而不是继续尝试读写。

### 8.2 半开连接与心跳

半开连接指一端认为连接仍存在、另一端已经离开或崩溃，双方可能长期无法发现。网络不会主动通知"对端进程被杀"，断电、拔网线、主机重启等情况可能让连接静默消失。TCP 自身的 `SO_KEEPALIVE` 默认关闭或探测间隔很长，只适合兜底，不适合及时发现故障。

可靠的做法是应用层心跳协议：双方定期发送 ping，收到 pong 或任意业务消息都刷新"最近活跃时间"。客户端在超过超时仍未收到任何数据时判定服务端不可达并重连；服务端定期扫描空闲连接，超过阈值时关闭，释放半开连接占用的资源。

心跳周期应显著小于故障容忍时间，但也不宜过短。例如每 30 秒发送一次心跳、连续 3 次未得到有效响应后判死，总检测时间约 90 秒；更严格的服务可以缩短到秒级，但会增加报文与唤醒开销。心跳消息应走与业务相同的帧格式，避免建立另一套解析规则。

### 8.3 发送成功不代表对端处理成功

`send` 返回成功只表示数据进入本端内核发送缓冲区。对端内核可能已经确认收到，但应用可能尚未处理；进程可能在处理过程中崩溃；响应可能在途中丢失。客户端不能因为 `send` 没有报错就认为请求已经生效。

因此客户端请求通常需要三层语义：

- 传输层：数据已交给内核；
- 协议层：服务端已收到完整请求并返回响应；
- 业务层：请求对应的事务已提交且可被查询或重复执行。

只有第二层和第三层语义符合业务预期时，调用方才算真正成功。超时后重试之前，应明确服务端可能执行过一次该请求，重试请求应携带幂等键，或者业务必须容忍重复执行。

### 8.4 优雅关闭与数据完整性

一端要主动结束时，直接 `close` 可能让尚未处理的数据留在对端接收缓冲区，对端下次读取时会先读到旧数据再看到 EOF，容易造成"请求已发送但响应未读完"的错误。更可靠的关闭顺序是：

1. 完成并刷新自己的最后一条消息；
2. 调用 `shutdown(SHUT_WR)`，向对端表达"发送方向已结束"；
3. 继续读取对端数据，直到读到 EOF 或达到关闭超时；
4. 最后 `close` 文件描述符。

这个顺序适合"我发完了，等你回复完再断"的场景。服务端处理完请求后通常也应先发完响应，再关闭连接。若关闭前套接字接收缓冲区中还有未读数据，直接关闭可能触发 RST，使对端无法收到我们已发出的最后响应；先读尽对端数据可以降低这种风险。

### 8.5 重复请求与幂等性

网络故障与超时意味着同一条消息可能被重复发送。TCP 会去重字节流中的重传，但应用层的超时重发会产生新的消息实例。服务端按连接顺序处理时，重复请求仍然可能被执行两次。

设计协议时可以为请求分配全局唯一 ID 或业务幂等键。服务端在处理前先检查是否已经见过该 ID，已处理则直接返回缓存的响应或幂等结果，未处理则执行并记录。由于记录本身也可能失败，真正严格的幂等还需要事务、去重表或业务状态机支撑。传输层的 `MSG_NOSIGNAL`、重连和重发都不能替代这层语义。

## 9. 完整示例：请求响应式互传

下面的示例把前面章节的机制组合成一个最小但完整的回显协议：客户端向服务端发送带 ID 的消息，服务端收到完整消息后把内容回传给客户端。两端都使用第 2 章的 `Socket`、第 3 章的 `WriteAll`/`ReadAll` 和第 4 章的帧编解码函数，因此这里只给出连接处理与主流程。

### 9.1 服务端

```cpp
#include <exception>
#include <thread>
#include <utility>
#include <vector>

void ServeEchoConnection(Socket connection)
{
    try {
        while (true) {
            const std::vector<std::uint8_t> frame =
                ReadFrame(connection.get());
            const Message request =
                DeserializeMessage(frame.data(), frame.size());

            Message response{};
            response.kind = request.kind;
            response.id = request.id;
            response.payload = "echo: " + request.payload;

            const std::vector<std::uint8_t> output =
                SerializeMessage(response);
            WriteAll(
                connection.get(),
                reinterpret_cast<const char*>(output.data()),
                output.size());
        }
    } catch (const std::exception& error) {
        // 连接结束或协议错误都从这里退出，
        // Socket 析构负责关闭文件描述符。
    }
}

int RunEchoServer(std::uint16_t port)
{
    Socket listener = MakeListeningSocket(port);
    for (;;) {
        Socket connection = AcceptConnection(listener);
        std::thread(&ServeEchoConnection, std::move(connection)).detach();
    }
}
```

服务端只处理"收到一帧、回复一帧"这一种逻辑，所以它可以阻塞等待完整帧。真实服务端还要考虑线程池、最大连接数、空闲超时、消息大小与协议错误码，而不是无限 `detach` 新线程。

### 9.2 客户端

```cpp
#include <cstdint>
#include <string>

void SendMessage(int fd, const Message& message)
{
    const std::vector<std::uint8_t> frame = SerializeMessage(message);
    WriteAll(
        fd,
        reinterpret_cast<const char*>(frame.data()),
        frame.size());
}

Message ReceiveMessage(int fd)
{
    const std::vector<std::uint8_t> frame = ReadFrame(fd);
    return DeserializeMessage(frame.data(), frame.size());
}

void RunEchoClient(const char* ip, std::uint16_t port)
{
    Socket connection = ConnectTo(ip, port);

    SendMessage(connection.get(), Message{1, 7, "hello from client"});
    const Message response = ReceiveMessage(connection.get());

    // response.id == 7
    // response.payload == "echo: hello from client"
}
```

客户端先完整发送一帧，再阻塞等待一帧。这个顺序在这个回显协议中成立，是因为服务端永远先读取再回复。对于服务端推送或并发请求场景，客户端必须能够随时读取消息，并把推送与请求响应分开处理，不能假设读取顺序恰好等于自己发送请求的顺序。

### 9.3 示例说明了什么

示例展示了双向传输的最小骨架：客户端发起请求，服务端读取并回写，客户端读取响应。它把问题拆成了几层：连接建立由 `Socket` 负责；字节流完整读写由 `WriteAll`/`ReadAll` 负责；消息边界与字段编码由帧函数负责；业务逻辑只处理完整 `Message`。每一层职责单一，网络细节不会泄漏到业务代码中。

示例的主要局限是同步阻塞模型和单请求等待。扩展到生产环境时，应把连接管理、读写调度、超时、重连和背压分别补上，而不是在业务回调中继续叠加 `recv`/`send` 细节。

## 10. 调试、测试与性能验证

### 10.1 先用系统工具模拟对端

在没有写完正式客户端或服务端之前，可以用系统工具验证基本连接与字节流行为。`nc` 可以连接监听端口并手工发送数据：

```text
nc 127.0.0.1 9090
hello
```

服务端日志应显示收到 `hello`，随后可观察服务端回写是否出现在终端。这类验证能快速确认监听、接受连接与基础读写没有方向性错误，但 `nc` 不会替你检查应用层帧格式，因此测试二进制帧仍需要专用客户端或脚本。

### 10.2 观察连接状态

Linux 上用 `ss` 查看连接与队列状态：

```text
ss -tnp
```

关注 `Recv-Q` 与 `Send-Q`：接收队列持续增长说明应用没有及时读取，发送队列持续增长说明对端没有及时读取或网络拥塞。连接状态也能帮助判断问题方向：大量 `CLOSE_WAIT` 表示本端应用没有关闭已收到 FIN 的连接；大量 `TIME_WAIT` 通常来自主动关闭方并会自然消退；`SYN_SENT` 长时间存在表示连接没有建立成功。

`TIME_WAIT` 是协议的正常机制，用来防止旧连接的延迟数据污染新连接。服务端频繁重启并绑定相同端口时，配合 `SO_REUSEADDR` 可以重新绑定；不应把 `TIME_WAIT` 的存在本身当作性能问题。

### 10.3 抓包验证行为

对协议正确性最有说服力的验证是抓包。本机调试可抓 loopback 接口：

```text
tcpdump -i lo port 9090 -nn
```

抓包可以看到握手序列号、数据分段、ACK、FIN 与 RST。要判断"为什么客户端认为服务端没有响应"，先看请求是否真的到达对端、对端是否真的发出了响应、响应是否因对端在发送前关闭而丢失。抓包还能验证 `TCP_NODELAY` 是否生效、是否存在过多小报文与重传。

### 10.4 边界与故障注入测试

网络代码的正确性问题大多出现在边界，而不是正常路径。至少应覆盖：

- 消息按任意位置拆包：发送端把一帧拆成 1 字节 + 剩余部分、半个头、头与正文交界，接收端都应正确拼回；
- 多条消息合并：一次写入多帧、两次写入在 TCP 层合并，解析都应逐帧完成；
- 超长长度与截断：声明长度超过上限应被拒绝，完整帧到达前断连应报错而不是挂死；
- 空消息与零长度正文：协议若允许，编解码应保持往返一致；
- 半关闭与 RST：对端 `shutdown(SHUT_WR)` 后仍发送、对端 `kill -9`、本端写已断开连接；
- 慢速消费者：客户端长时间不读取，服务端发送队列与内存不能无限增长；
- 重复与乱序响应：并发请求的 ID 对应必须正确，旧连接的延迟响应不能污染新连接。

编解码器可以脱离网络单独做单元测试：给定任意字节序列，验证能解析出多少完整帧以及残留多少半帧。连接级行为则需要进程级集成测试，把超时缩短到秒级以内，并让客户端和服务端分别记录收发序号。

### 10.5 性能观察指标

性能测试不能只报告吞吐量。互相传输场景还应当观察：

- 平均与尾延迟，尤其是 99%/99.9% 分位；
- 每秒完成的消息或请求数；
- 系统调用次数与数据拷贝次数；
- CPU 使用率、上下文切换与线程数量；
- 发送队列与接收队列长度、重传率、丢包率；
- 单连接内存占用与整体内存增长。

本机 loopback 测试排除了真实网络的 RTT、丢包与带宽影响，适合验证协议和 CPU 路径，但不能代表公网或跨机房部署。应先在目标网络环境建立基线，再做协议、缓冲和并发模型上的改动；避免在没有数据的情况下用 `TCP_NODELAY`、改缓冲区或引入复杂事件循环替代真正的瓶颈修复。

## 11. 机制比较与工程原则

### 11.1 TCP 与 UDP

需要可靠有序的长时间双向传输时选 TCP，应用不需要自己实现确认、重传与排序。UDP 只在数据报语义、低延迟或组播广播带来明确收益时使用，此时必须显式接受丢失与乱序，或自建可靠性。用"TCP 多一次握手所以慢"作为选择 UDP 的理由往往不充分，真实瓶颈可能在其他层。

### 11.2 每连接一线程与事件循环

每连接一线程把并发隐藏在操作系统调度中，适合连接少、每条连接处理时间长的服务。事件循环适合大量空闲连接和短消息，但要求任何回调都不能阻塞事件线程。选择应以连接数量与处理模型为准，而不是跟随潮流。工程上可以先实现阻塞模型验证协议，再按连接规模演进。

### 11.3 帧格式

二进制长度前缀是大多数自定义 TCP 协议的合理默认：实现直接、可以预先检查长度、适合二进制负载。分隔符适合人工可读的文本协议，固定长度适合最稳定的简单记录。无论选哪种，都要规定最大长度、空消息语义和错误处理，并保证解析器可以处理任意分片。

### 11.4 内核保活与应用心跳

`SO_KEEPALIVE` 只能作为长期兜底，默认周期太长且不携带业务信息。需要快速发现死连接、空闲清理和会话存活判断时，应使用应用层心跳，并把最近活跃时间作为连接级状态维护。心跳与业务消息应共用帧格式，避免另一套解析路径。

### 11.5 序列化

自定义协议应显式编码字段并使用定宽整数，不能直接发送本地结构体内存。简单文本协议便于调试，但长度、转义和性能需要额外处理；JSON/Protobuf 等现成格式能减少编码工作量，但要控制消息上限并处理解析异常。任何线上格式都应包含版本演进策略。

### 11.6 设计检查清单

- 明确连接生命周期：谁发起、谁结束、半关闭是否使用、超时如何判定；
- 明确帧格式：头字段宽度、字节序、长度是否含头、最大长度；
- 明确读写所有权：每条连接的读、写、关闭在同一时间只由一个执行单元负责；
- 明确接收缓冲：半帧如何保留、完整帧如何取出、队列上限是多少；
- 明确错误分类：`EAGAIN` 重试、EOF 关闭、RST 丢弃、超时清理；
- 明确发送确认：应用层何时才算"对端已处理"，重试是否幂等；
- 明确资源上限：连接数、线程数、内存、任务队列、日志频率；
- 先写测试再优化，用抓包和故障注入验证协议，不要只靠正常路径演示。

## 结语

客户端与服务端之间的互相传输，本质上是把两个独立的执行上下文通过字节流或数据报连接起来。可靠实现不能只依赖"调用一次发送、调用一次接收"的直觉：TCP 会拆分与合并数据，应用必须自行维护消息边界；读写可能只完成部分，程序必须循环处理完整长度；连接可能正常关闭、被复位或在双方不知情时消失，故障处理必须成为协议的一部分。

工程上应把问题分层：RAII 管理描述符，明确读写与关闭所有权；用长度前缀等协议格式定义消息边界；用显式序列化保证字段一致；用接收缓冲和发送队列处理任意分片与背压；用超时与心跳检测死连接；用消息 ID、幂等键保证请求与响应的对应和业务语义。先把这些基础做对，再根据连接数量和处理成本选择每连接一线程、事件循环或混合模型，才能让 C++ 客户端与服务端在网络传输上既正确又可维护。
